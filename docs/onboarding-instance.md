# Развёртывание клиентского инстанса

Модель продажи — instance-per-client: каждому клиенту свой VPS и свой инстанс
(изоляция данных — часть оффера, см. `docs/business-launch-plan.md`).
Целевое время развёртывания — 30 минут без учёта DNS/TLS.

## Предпосылки

- Linux VPS (2 vCPU / 4 GB RAM / 40 GB SSD достаточно для старта), Docker + compose v2.
- Домен клиента (например `wms.client.ru`) с A-записью на VPS.
- Доступ по SSH.

## Шаги

### 1. Код на сервер

```bash
sudo mkdir -p /var/www/app-prod && sudo chown "$USER" /var/www/app-prod
git clone <репозиторий> /var/www/app-prod   # или rsync с рабочей машины
cd /var/www/app-prod
git checkout <тег-релиза>                    # клиент пиннится на тег, не на main
```

### 2. Инстанс одной командой

```bash
./scripts/onboarding/new-instance.sh --admin-email admin@client.ru
```

Скрипт генерирует `.env.prod` (секреты), поднимает контейнеры (alembic
выполняется на старте backend), ждёт `/health` и создаёт администратора.
Пароль печатается один раз — передать владельцу, сменить при первом входе.
Повторный запуск безопасен: секреты и существующий админ не трогаются.

### 2а. Несколько инстансов на одном VPS (маленькие клиенты)

Каждому инстансу — свой каталог с собственным checkout (это же даёт пиннинг
на разные теги), своё имя и своя пара портов:

```bash
git clone <репозиторий> /var/www/client-b && cd /var/www/client-b
./scripts/onboarding/new-instance.sh --name client-b \
    --backend-port 10100 --frontend-port 10180 --admin-email admin@client-b.ru
```

Имя (`--name`) задаёт compose-проект и префикс контейнеров — тома с данными
БД полностью изолированы между инстансами. Порты и имя записываются в
`.env.prod` инстанса; повторные запуски и обновления читают их оттуда, флаги
повторять не нужно. Конвенция портов: первый инстанс 10000/10080, дальше
+100 (10100/10180, 10200/10280, ...).

Правила размещения: не больше 2–3 небольших клиентов на VPS (8 ГБ RAM),
крупных не селить вместе; вырос клиент — переезд на выделенный VPS
(дамп БД + uploads + этот же скрипт).

### 3. nginx + TLS на хосте

Контейнеры слушают только loopback: backend `127.0.0.1:10000`, frontend
`127.0.0.1:10080` (у второго инстанса — его порты из `.env.prod`). На хосте —
nginx, по одному `server` на домен инстанса: `/` → frontend-порт, `/api/` →
backend-порт (срезая `/api`), `/uploads/` → backend-порт (файлы раздаёт
backend с авторизацией; публичного статика-маунта нет). TLS — certbot.
Референс конфигурации — `nginx/nginx.conf`.

### 4. Бэкапы (обязательно до передачи клиенту)

```bash
cp scripts/backup/wms-backup.env.example /etc/wms-backup.env  # заполнить
./scripts/backup/install-cron.sh
```

БД + uploads + код, ежедневно 03:00 МСК. Проверить: запустить `wms-backup.sh`
вручную и убедиться, что архив появился. Восстановление — `wms-restore.sh`.
Бэкапы обещаны в оффере («ежедневные бэкапы») — инстанс без них клиенту не передаём.

Второй инстанс на том же VPS: свой конфиг `/etc/wms-backup-<имя>.env`
(в нём — контейнеры `wms_<имя>_db`/`_backend` из `.env.prod` инстанса, свой
`APP_DIR`, `UPLOADS_DIR`, `BACKUP_ROOT`) и своя строка в `/etc/cron.d/wms-backup`
с `WMS_BACKUP_ENV_FILE=/etc/wms-backup-<имя>.env` (поддерживается `wms-backup.sh`).

### 5. Настройка под клиента (в UI, вместе с клиентом — это часть внедрения)

1. Справочники: клиенты (селлеры), поставщики, перевозчики, точки логистики,
   «Наши склады» (+ ставка аренды), должности.
2. Тарифы: упаковка (по товару×клиенту), палеты, короба, логистика.
3. Пользователи и роли (admin / manager / warehouse_manager / shift_supervisor /
   warehouse_head), сотрудники и ставки для табеля.
4. Ячейки адресного хранения и QR-этикетки — если клиент использует.

### 6. Мобильное приложение (если нужно клиенту)

APK собирается под домен инстанса: `VITE_API_BASE_URL=https://wms.client.ru/api`
на сборке (см. docs/mobile-plan.md и память проекта по сборке APK).
Push-уведомления требуют Firebase-проект и `FIREBASE_CREDENTIALS_FILE` — опционально.

## Обновление инстанса

```bash
cd /var/www/app-prod
git fetch && git checkout <новый-тег>
docker compose --env-file .env.prod -f docker-compose.prod.yml up -d --build
```

Alembic докатит схему на старте backend. GitHub Actions деплоит только НАШИ
test/prod (ADR 0001) — клиентские инстансы обновляются по тегам вручную,
пока их мало.

## Контракт переменных окружения

Единственный источник — `.env.prod.example` (полный список с комментариями).
Правило для доработок: новая переменная окружения в коде = обновление
`.env.prod.example` в том же коммите.
