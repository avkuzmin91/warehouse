# ADR 0001: CI-only deployment via GitHub Actions (test + prod)

## Status

Accepted (целевая модель; базовая реализация CI — `.github/workflows/deploy.yml` + `deploy-environment.yml`; emergency runbook — отдельно).

## Context

В проекте сосуществовали два пути выкладки: GitHub Actions (rsync/SSH + `docker compose`) и ручной `scripts/deploy.sh` на VPS. Это давало расхождение окружений, разный контракт compose/путей, отсутствие единого release flow и health gate в CI, общий SSH-доступ к test/prod без явной границы ответственности.

Требуется зафиксировать **целевую** модель до правок в `.github/workflows/`, серверных путях и документации.

## Decision

1. **CI-only для нормальной выкладки.** Единственный поддерживаемый способ доставить **новую версию** приложения на **test** и **prod** — через **GitHub Actions**, по согласованным триггерам (ветки / при необходимости теги — см. инварианты ниже).

2. **`scripts/deploy.sh` (и связанные алиасы)** не участвуют в **обычном** релизном процессе. Их использование допускается только как **emergency / диагностика / runbook** (восстановление после инцидента, ручной smoke, расследование), с явной фиксацией в инциденте «почему не через CI».

3. **Единый pipeline для test и prod.** Один и тот же набор шагов (логически): получить определённый ref из GitHub → доставить на сервер согласованным способом → поднять стек через **один и тот же контракт** `docker compose` (те же `-f` / те же имена проектов, что задокументированы для окружения) → **обязательный health gate** → (при необходимости) smoke. Отличия **только** в: GitHub Environment, секретах, хосте/пути на диске, имён веток-триггеров.

4. **Rollback.** Откат версии — только через **повторную выкладку известного good** (предыдущий **SHA** или **тег**), инициированную через CI (re-run workflow с ref, workflow_dispatch с input, или отдельный задокументированный механизм). **Не** считать откатом правки файлов/образов «вручную на сервере» без воспроизводимого ref.

## Invariants (нельзя нарушать без нового ADR)

| # | Инвариант |
|---|-----------|
| I1 | **Единственный источник релиза** — GitHub: ветки и коммиты (**SHA**); при использовании тегов — тег указывает на тот же объект в Git. |
| I2 | **CI — единственный способ** выкатить новую версию на **test** и **prod** в штатном процессе. |
| I3 | **Manual scripts** (`deploy.sh` и пр.) — **только** аварийные операции и диагностика, не штатный релиз. |
| I4 | **Одинаковый pipeline** для test и prod; различия — **env / секреты / хост / путь**, не «другая последовательность шагов». |
| I5 | После деплоя в CI — **обязательный health gate** (и при принятой политике — дополнительный smoke); падение gate = **неуспешный** деплой с остановкой job. |
| I6 | **Rollback** — через предыдущий **SHA** / **тег**, воспроизводимо через CI, без «ручного правления продакшена» как нормы. |

## Release contract (кратко)

- **Что считается выкатанным:** конкретный **SHA** (и опционально **тег**), зафиксированный в логе успешного workflow после прохождения health gate.
- **Связь веток (текущая политика репозитория):** интеграция — **`develop`** → test; продакшен — **`main`** → prod. Изменение веток — только через обновление этого ADR и workflows.
- **Миграции БД:** должны быть частью **одного** release flow (явный шаг в pipeline или жёстко задокументированный порядок до/после `compose up` в runbook CI); не оставлять «немой» разрыв между кодом и схемой.

## Consequences

- **Плюсы:** один источник истины для выкладки, проще аудит и инциденты, единый контракт для test/prod, возможность централизованно добавить concurrency, approvals (GitHub Environments), артефакты.
- **Минусы:** при недоступности GitHub Actions нужен **emergency runbook** (в т.ч. через `deploy.sh` или ручной повтор последнего известного good ref — с постфактум синхронизацией с репозиторием).
- **Обязательные последующие шаги:** runbook emergency; явный шаг миграций в CI при принятии политики; периодическая сверка серверных путей с `deploy.yml`.

## Out of scope

- Выбор registry vs build-on-server vs rsync — не фиксируется в этом ADR; важно только соблюдение инвариантов и одного pipeline по **шагам**, а не конкретная реализация доставки битов.
- Масштабирование за пределы одного VPS — не цель данного решения.
