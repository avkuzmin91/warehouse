# COMPONENT: Collection Actions

---

# 1. Цель

Определить набор действий над коллекцией внутри FiltersPanel.

---

# 2. Контекст использования

- Всегда используется внутри FiltersPanel

---

# 3. Назначение

Содержит действия, относящиеся ко всему списку:

- создание нового элемента
- (расширяемо: экспорт, bulk actions)

---

# 4. Состав

---

## 4.1 Primary Action

### Создание (Create)

- иконка "+"
- переход: /{entity}/new

---

## 4.2 Secondary Action

### Сброс фильтров (Reset Filters)

- очищает Query State (filters)
- сбрасывает URL (page = 1)
- вызывает reload списка

---

# 5. UI размещение

---

- справа внутри FiltersPanel
- рядом с фильтрами
- визуально отделено spacing’ом

---

# 6. Поведение

---

## Create

- navigation only
- не влияет на state

---

## Reset

- очищает filters
- не сбрасывает сортировку
- reload данных

---

# 7. Ограничения

- запрещено использовать вне FiltersPanel
- запрещено добавлять API логику
- запрещено дублировать UI в таблицах

---

# 8. Архитектурное правило

FiltersPanel = Filters + CollectionActions

---

# 9. Итог

Collection Actions = встроенный блок управления списком внутри FiltersPanel

---

# # ENTITY PAGE PATTERNS (Create / Edit / View)

------

# 1. Цель

Определить единый стандарт построения страниц:

- создания сущности (Create)
- редактирования сущности (Edit)
- просмотра сущности (View / Detail)

Применяется ко всем доменным объектам:

- товары
- клиенты
- справочники
- любые сущности системы

------

# 2. Область применения

Обязательно используется для страниц:

- `/dictionaries/*`
- `/clients/*`
- `/inventory/*`
- любых entity routes

------

# 3. Базовая концепция

Каждая entity-страница строится по единому паттерну:

```
PageContainer
  Breadcrumbs
  Form / View Content
  Optional: System Info Block
  ActionBar
```

------

# 4. Типы страниц

## 4.1 Create Page

- создание новой сущности
- пустая форма
- отправка POST

Маршрут:

```
/{entity}/new
```

------

## 4.2 Edit Page

- редактирование существующей сущности
- форма предзаполнена
- отправка PATCH/PUT

Маршрут:

```
/{entity}/{id}
```

------

## 4.3 View Page

- только просмотр данных
- без редактирования
- может совпадать с edit UI в readOnly режиме

------

# 5. Глобальная структура UI

## 5.1 Общая структура

```
<PageContainer>

  <Breadcrumbs />

  <EntityForm | EntityView />

  <SystemInfoBlock /> (optional)

  <ActionBar />

</PageContainer>
```

------

# 6. Form Pattern (Create / Edit)

## 6.1 Общие правила

- форма вертикальная
- поля соответствуют Data Model
- обязательные поля помечаются `*`
- единый validation flow

------

## 6.2 Поведение формы

### Create

- форма пустая
- default values применяются (если есть)
- POST запрос

------

### Edit

- данные загружаются через API
- форма инициализируется данными
- PATCH/PUT запрос

------

# 7. View Pattern (Read-only)

## 7.1 Поведение

- все поля read-only
- input заменяется на text display
- кнопки редактирования отсутствуют или disabled

------

# 8. ActionBar (глобальный компонент)

Используется во всех Create/Edit страницах

## 8.1 Содержит:

- Primary Action (Сохранить / Создать)
- Secondary Action (Отмена)

------

## 8.2 Поведение:

### Сохранить / Создать

- выполняет валидацию
- отправляет API запрос
- redirect после успеха

------

### Отмена

- переход назад в список
- изменения не сохраняются

------

# 9. SystemInfoBlock (аудит данные)

## 9.1 Назначение

Отображение системных данных сущности

------

## 9.2 Поля:

- created_at
- created_by
- updated_at
- updated_by

------

## 9.3 Правила:

- только read-only
- только Edit и View режимы
- Create не содержит

------

# 10. Breadcrumb Pattern

Общий компонент:

- строится автоматически из URL
- последняя крошка зависит от режима:

### Create:

```
Создание {Entity}
```

### Edit:

```
Редактирование {Entity}
```

### View:

```
Просмотр {Entity}
```

------

# 11. Loading Pattern

## 11.1 Edit / View

- loader во время GET /{id}
- форма disabled до загрузки

------

## 11.2 Create

- loader только при инициализации (если есть defaults)

------

# 12. Error States

## 12.1 Not Found

- entity не существует
   → экран "Не найдено"

------

## 12.2 API Error

- отображается toast / inline error
- форма не сбрасывается

------

# 13. Navigation Rules

## 13.1 Open Edit

- клик по строке таблицы
   → `/entity/{id}`

------

## 13.2 Open Create

- кнопка "Создать"
   → `/entity/new`

------

## 13.3 Cancel

- возврат в список
   → `/entity`

------

# 14. UI Rules

- PageContainer обязателен
- max-width зависит от типа страницы:
  - list: 1200
  - form: 640
- без modals для CRUD
- без inline edit

------

# 15. Integration Rules

Использует глобальные системы:

- SYSTEM: Query State Management (для list)
- COMPONENT: Breadcrumbs
- COMPONENT: ActionBar
- COMPONENT: SystemInfoBlock

------

# 16. Итог

Этот документ заменяет необходимость дублировать:

- create page MD
- edit page MD
- view page MD

Они теперь описываются как **вариации одного паттерна**, а не отдельные спецификации.

### Источник: `Filters Panel.md`

# COMPONENT: FILTERS PANEL

---

# 1. Цель

Универсальный композиционный компонент для управления списками сущностей.

Объединяет:

- фильтрацию данных
- управление Query State
- синхронизацию с URL
- действия над коллекцией (Collection Actions)

---

# 2. Область применения

Используется на list-страницах:

- справочники
- товары
- клиенты
- пользователи
- любые таблицы

---

# 3. Общая структура

Компонент состоит из двух зон: [ Filters ] -------------------- [ Collection Actions ]

---

# 4. UI структура

---

## 4.1 Расположение

- в соответствии с PageContainer
- в соответствии с List Page Pattern

---

## 4.2 Визуальная структура

- горизонтальный flex layout
- gap: 12–16px
- элементы фильтров слева
- действия (actions) справа
- wrap на mobile

---

# 5. Filters (левая часть)

---

## 5.1 Поддерживаемые элементы

### Search

- текстовый input
- debounce 300–500ms

---

### Select

- типизированные значения
- зависит от сущности

---

### Boolean filter

- Да / Нет

---

## 5.2 Поведение

- изменение → update Query State
- update → API reload
- синхронизация с URL

---

# 6. Collection Actions (правая часть)

- будет описано в ТЗ для Collection Actions

---

## 6.3 Ограничения

- не содержит бизнес-логики
- не выполняет API запросы напрямую
- полностью зависит от Query State

---

# 7. State Model

```ts
{
  search?: string,
  type?: string,
  is_active?: boolean,
  page: number,
  limit: number,
  sort?: string
}
```

# 8. URL синхронизация

------

## Пример

```
/dictionaries/products?search=shirt&type=clothes&page=1
```

------

## Правила

- UI ↔ URL синхронизированы
- URL — источник состояния при загрузке

------

# 9. API интеграция

```
GET /products
```

------

## Правила

- пустые поля не отправляются
- формируется единый query object

------

# 10. Ограничения

- запрещено хранить state только локально
- запрещено разделять actions и filters
- запрещено использовать без Query State Management

------

# 11. Сценарии тестирования

- поиск с debounce
- select фильтрация
- reset filters
- create navigation
- восстановление состояния из URL

---

**LIST PAGE PATTERN**

# 1. Цель

Определить стандарт сборки страниц списков сущностей.

Обязательно для:

- справочников
- товаров
- клиентов

---

# 3. Концепция

List Page = композиция:

- Query State Management
- Filters + Actions (Filters Panel)
- Sorting
- Pagination
- Table
- Navigation

---

# 4. Базовая структура

<PageContainer>  <Breadcrumbs />  <FiltersPanel />  <Table />  <Pagination /> </PageContainer>

- синхронизация с Query State

## 6.3 Навигация


------

### Create button (через FiltersPanel)

```

```

------

# 7. Состояния

------

------

------

# 8. Query State Integration

------

## Хранит:

- filters
- sort
- page
- limit

------

## Источник истины:

- URL + Query State

------

# 9. UI правила

- PageContainer обязателен
- maxWidth определяется контейнером
- адаптивность обязательна

------

# 10. Ограничения

- запрещено inline edit
- запрещены модалки для CRUD
- запрещено хранить state вне Query State

------

# 11. Зависимости

Использует:

- PageContainer

- Pagination
- Query State Management

# `Page Container` (UI Layer — только оболочка)

# 1. Цель

Определить единый UI-контейнер страниц приложения.

Отвечает только за:

- визуальную структуру страницы
- центрирование
- ограничение ширины
- единый стиль карточки

------

# 2. Область применения

Используется на всех страницах, кроме:

- `/auth`
- `/auth/register`

------

# 3. Концепция

PageContainer — это **визуальная оболочка**, внутри которой размещаются любые страницы:

- списки
- формы
- карточки
- настройки

------

# 4. Структура

```
<PageContainer>
  <Breadcrumbs />
  {children}
</PageContainer>
```

------

# 5. UI правила

## 5.1 Центрирование

- контейнер всегда по центру экрана
- horizontal center alignment

------

## 5.2 Ограничение ширины

- max-width задаётся извне (через страницу или паттерн)
- PageContainer НЕ принимает бизнес-решения

------

## 5.3 Внешний вид

- фон страницы — системный
- контейнер — card UI
- border-radius: 12–16px
- мягкая тень
- padding внутри контейнера

------

## 5.4 Адаптивность

- desktop: фиксированный max-width
- tablet: уменьшенные отступы
- mobile: full width + padding

------

# 6. Запрещено

PageContainer НЕ должен содержать:

- таблицы
- фильтры
- пагинацию
- кнопки действий
- бизнес-логику страниц

------

# 7. Ответственность

PageContainer отвечает только за:

- layout
- визуальный контейнер
- структуру страницы

------

# 8. Исключения

Auth страницы используют:

- `AuthLayout`

------

# 9. Итог

PageContainer = **чистый UI shell без логики**

### Источник: `Pagination.md`

# COMPONENT: Pagination

---

# 1. Цель

Реализовать универсальный компонент пагинации для списков данных.

Компонент используется на страницах:

- справочник товаров
- справочник клиентов
- другие списки системы

---

# 2. Зависимости

Использует:

- SYSTEM: Query State Management

---

# 3. Назначение

Компонент отвечает за:

- переключение страниц
- выбор количества элементов на странице
- синхронизацию состояния с URL
- триггер загрузки данных

---

# 4. UI структура

Компонент содержит:

- Переключение страниц (вперёд / назад)
- Номера страниц
- Выбор количества элементов на странице

---

## 4.1 Переключение страниц

Элементы:

- Кнопка "Назад"
- Кнопка "Вперёд"
- Номера страниц

---

### Поведение:

- текущая страница подсвечена
- кнопка "Назад" disabled на первой странице
- кнопка "Вперёд" disabled на последней странице

---

## 4.2 Выбор количества элементов

Dropdown:

- 20 строк
- 50 строк
- 100 строк

По умолчанию:

- 20 строк

---

# 5. Поведение

---

## 5.1 Изменение страницы

При выборе страницы:

- обновляется query param: page
- вызывается обновление данных

---

## 5.2 Изменение лимита

При изменении limit:

- обновляется query param: limit
- page сбрасывается в 1
- вызывается обновление данных

---

## 5.3 Синхронизация с URL

Состояние хранится в query params:

Пример:

/dictionaries/products?page=2&limit=50

---

## 5.4 Интеграция с Query State

Компонент НЕ хранит состояние локально.

Он:

- читает page, limit из Query State
- обновляет Query State при изменениях

---

# 6. API требования

Backend должен поддерживать:

GET /resource

Параметры:

- page (number)
- limit (number)

---

### Ответ:

```json
{
  "items": [],
  "total": 100,
  "page": 1,
  "limit": 20
}
```

# 7. UI требования

- размещается под таблицей
- выравнивание: справа
- отступ сверху от таблицы
- адаптивность

------

# 8. Ограничения

- не использовать локальное состояние вне Query State
- не дублировать логику пагинации на страницах

------

# 9. Проверка

------

## Сценарий 1: Переключение страницы

1. Нажать на страницу "2"

Ожидается:

- URL обновился: page=2
- загрузились новые данные

------

## Сценарий 2: Изменение limit

1. Выбрать 50 элементов

Ожидается:

- limit=50
- page=1
- данные обновились

------

## Сценарий 3: Граничные состояния

1. Перейти на первую страницу

Ожидается:

- кнопка "Назад" disabled

------

## Сценарий 4: URL синхронизация

1. Открыть:

/dictionaries/products?page=3&limit=100

Ожидается:

- отображается 3 страница
- лимит = 100

### Источник: `Sorting.md`

# COMPONENT: SORTING

---

# 1. Цель

Реализовать универсальный механизм сортировки данных в таблицах.

Компонент предназначен для:

- изменения порядка отображения данных
- управления параметрами сортировки
- интеграции с Query State и API

---

# 2. Область применения

Используется:

- в таблицах (Table Component)
- на страницах списков (products, clients и др.)

---

# 3. Общая концепция

Сортировка осуществляется через клики по заголовкам колонок таблицы.

---

# 4. UI поведение

---

## 4.1 Триггер сортировки

Сортировка вызывается:

- кликом по заголовку колонки

---

## 4.2 Состояния сортировки

Каждая колонка может иметь 3 состояния:

1. Нет сортировки
2. По возрастанию (asc)
3. По убыванию (desc)

---

## 4.3 Переключение

При каждом клике:

```text
нет → asc → desc → нет
```

## 4.4 Визуализация

- отображается иконка:
  - ↑ для asc
  - ↓ для desc
- активная колонка визуально выделяется

------

# 5. Поведение

------

## 5.1 Изменение сортировки

При клике:

- обновляется sort в Query State
- обновляется URL
- выполняется API запрос

------

## 5.2 Сброс сортировки

Если состояние возвращается в "нет":

- параметр sort удаляется из URL
- выполняется запрос без сортировки

------

## 5.3 Одна активная сортировка

- допускается сортировка только по одной колонке

------

# 6. Интеграция с Query State

------

## 6.1 Формат

```typescript
sort: {
  field: string,
  direction: "asc" | "desc"
}
```

## 6.2 Пример

/dictionaries/products?sort=created_at_desc

---

## 6.3 Формирование параметра

sort = {field}_{direction}

Примеры:

- name_asc
- created_at_desc

# 7. API интеграция

------

## 7.1 Запрос

GET /products?sort=name_asc

---

## 7.2 Требования к backend

- валидировать поле сортировки
- валидировать направление
- игнорировать некорректные значения

------

# 8. Ограничения

- не использовать клиентскую сортировку
- не допускать множественную сортировку (multi-sort)
- не хранить состояние только в UI

------

# 9. Безопасность

- backend проверяет допустимые поля
- frontend не доверяется

------

# 10. Сценарии тестирования

------

## Сценарий 1: Сортировка по возрастанию

1. Нажать на колонку "Название"

Ожидается:

- sort=name_asc
- данные отсортированы

------

## Сценарий 2: Сортировка по убыванию

1. Нажать повторно

Ожидается:

- sort=name_desc

------

## Сценарий 3: Сброс

1. Нажать третий раз

# **SYSTEM: Soft Delete Policy**

---

# 1. Цель

Определить единый стандарт удаления данных в системе.

---

# 2. Основной принцип

В системе НЕ существует физического удаления данных через UI.

Любое удаление:

→ это всегда soft delete  
→ данные сохраняются в базе  
→ доступ к ним может быть восстановлен через backend/БД

---

# 3. Модель удаления

---

## 3.1 Общий подход

Любая сущность поддерживает поле:

is_deleted: boolean

или расширенный вариант:

deleted_at: datetime | null
deleted_by: string | null

---

## 3.2 Рекомендуемый стандарт

is_deleted: boolean
deleted_at: datetime
deleted_by: string

---

# 4. Поведение системы

---

## 4.1 Удаление через UI

Любая операция "Удалить":

- НЕ вызывает DELETE entity
- выполняет:

PATCH /{entity}/{id}
 {
 is_deleted: true
 }

---

## 4.2 Скрытие данных

По умолчанию:

- все GET запросы возвращают только:

is_deleted = false

---

## 4.3 Админ режим (опционально)

Администратор может видеть удалённые записи:

- через фильтр:
  - include_deleted = true

---

# 5. API правила

---

## 5.1 Запрещено

DELETE /entity/{id}

запрещено использовать в UI

---

## 5.2 Разрешено

PATCH /entity/{id}

с установкой:

is_deleted = true

---

# 6. Восстановление данных

---

## 6.1 Возможность восстановления

Администратор может восстановить запись:

PATCH /entity/{id}
 {
 is_deleted: false
 }

---

## 6.2 Источник истины

Восстановление всегда происходит:

- через backend
- либо напрямую через БД (fallback)

---

# 7. UI поведение

---

## 7.1 Кнопка "Удалить"

- НЕ удаляет запись физически
- вызывает soft delete
- может отображаться как:
  - "Удалить"
  - или "Деактивировать" (рекомендуется для UX)

---

## 7.2 Состояния

### Активная запись:
- отображается в списках

### Удалённая:
- скрыта по умолчанию

---

# 8. Audit trail

---

При удалении сохраняется:

- deleted_at
- deleted_by

---

# 9. Безопасность

---

- удаление доступно только admin
- backend обязан игнорировать попытки hard delete
- frontend НЕ может управлять типом удаления

---

# 10. Ограничения

---

- запрещено физическое удаление через API UI слоя
- запрещено каскадное удаление без soft delete логики
- запрещено обходить is_deleted фильтр без явного флага

## 1. Цель

Реализовать глобальный header (шапку приложения), отображаемый на всех страницах после авторизации.

Компонент предназначен для:
\- навигации
\- выхода из системы
\- отображения текущего пользователя

---

## 2. Область применения

Header отображается на всех страницах:

\- /home
\- /dictionaries/*
\- /inventory/*
\- другие защищённые страницы

---

## 3. Не отображается на страницах

\- /auth
\- /auth/register

---

## 4. UI структура

### 4.1 Общая структура

Header располагается в верхней части экрана и содержит:

\- название компании (слева)
\- кнопку выхода (справа)

---

### 4.2 Название компании

\- используй логотип \logo\logo main.png
\- кликабельно

Поведение:
→ переход на /home

---

### 4.3 Кнопка выхода

\- отображается справа
\- в виде иконки (logout)

---

## 5. Поведение

### 5.1 Выход из системы

При нажатии:

\- удалить JWT токен из localStorage
\- очистить пользовательские данные (если есть)
\- редирект на /auth

---

### 5.2 Доступ

\- header отображается только для авторизованных пользователей

---

## 6. Техническая реализация (Frontend)

\- реализовать как общий компонент
\- подключать через layout (AppLayout)

\```jsx
<AppLayout>

  <Header />
  <Outlet />
</AppLayout>

# 7. UI требования

- фиксирован в верхней части (sticky или fixed)
- занимает всю ширину
- горизонтальное выравнивание:
  - слева — название
  - справа — logout
- отступы по краям
- лёгкая тень (опционально)

------

# 8. Ограничения

- не дублировать header в отдельных страницах
- не реализовывать logout локально на страницах

------

# 9. Безопасность

- logout удаляет токен
- backend должен проверять токен при каждом запросе

------

# 10. Проверка

## Сценарий 1

1. Войти в систему
2. Перейти на любую страницу

Ожидается:

- header отображается

------

## Сценарий 2

1. Нажать logout

Ожидается:

- токен удалён
- редирект на /auth

------

## Сценарий 3

1. Открыть /auth

Ожидается:

- header отсутствует

# ГЛОБАЛЬНЫЙ КОМПОНЕНТ: ХЛЕБНЫЕ КРОШКИ (BREADCRUMBS)

---

# 1. Цель

Реализовать глобальный компонент хлебных крошек для навигации по приложению.

Компонент предназначен для:
- отображения текущего пути пользователя
- упрощения навигации между уровнями страниц
- стандартизации UI навигации

---

# 2. Область применения

Breadcrumbs отображаются на внутренних страницах приложения, в том числе:

- **/home** — одна крошка «Главная» (текущая страница, без ссылок выше)
- /dictionaries и вложенные маршруты
- /inventory
- /dictionaries/products/* и прочие разделы
- /users
- другие защищённые страницы
- экраны «Проверка доступа…» (ожидание проверки роли) и страница 403 (при отображении в рамках защищённого layout)

---

# 3. Не отображается

Компонент НЕ отображается на страницах:

- /auth
- /auth/register

---

# 4. Структура компонента

Breadcrumbs представляет собой цепочку навигационных элементов:

Пример (между сегментами — пробелы вокруг разделителя «/»):

`Главная / Справочники / Товары / Создание товара`

(визуально: неразрывный пробел, «/», пробел, затем следующий сегмент)

---

# 5. Поведение

## 5.1 Формирование

- путь формируется автоматически на основе текущего URL (`useLocation` → `pathname`)
- каждый сегмент URL преобразуется в читаемое название (см. п. 6)
- логика маппинга вынесена в отдельный модуль (например, `utils/breadcrumbLabels.ts`)

---

## 5.2 Навигация

- все элементы, кроме последнего, кликабельны
- последний элемент (текущая страница) не кликабелен, с атрибутом `aria-current="page"`

---

## 5.3 Пример

URL: /dictionaries/products/new

Отображение: Главная / Справочники / Товары / Создание товара

---

# 6. Правила отображения названий

## 6.1 Статические маппинги (фрагменты пути)

- `home` → Главная
- `dictionaries` → Справочники
- `products` → Товары
- `users` → Пользователи
- `inventory` → Учет товаров
- сегменты разделов справочника: `clients` → Клиенты, `colors` → Цвета, `sizes` → Размеры и т.д.

---

## 6.2 Создание и формы

- сегмент `new` после известного раздела справочника → осмысленный заголовок, например «Создание товара», «Создание клиента» (зависит от родительского сегмента)
- сегмент `new` без подходящего контекста → **Создание**

---

## 6.3 Динамические сегменты

- идентификатор карточки (в пути `/dictionaries/{section}/{id}`) → **Карточка**
- сегмент `edit` → **Редактирование**

---

# 7. UI требования

## 7.1 Размещение

- хлебные крошки отображаются **в верхней части основного контента**
- **внутри стеклянной карточки** (класс `auth-card` / тот же визуальный контейнер, что и формы, таблицы, списки)
- **первый дочерний блок** внутри `<section class="auth-card …">` (сразу под «стеклом»), **не** вынесены в отдельную полосу над карточкой и **не** в общем `AppLayout` над `<Outlet />`
- на внутренних страницах **отдельный заголовок уровня h1** под крошками **не** используется: наименование текущего раздела — в **последней крошке** (исключения: экраны `/auth` и `/auth/register` без крошек, со своим заголовком)

## 7.2 Внешний вид

- горизонтальное расположение, перенос строки при нехватке ширины (flex, wrap)
- разделитель между сегментами: символ «/» с **пробелами с обеих сторон** (в т.ч. визуально устойчивые к схлопыванию пробелов в вёрстке, например `white-space: pre` у разделителя)
- **цвета** (согласованы с ранее использовавшимися `dict-breadcrumbs`):
  - обводка цепочки: нейтральный приглушённый текст
  - кликабельные сегменты: акцентный (primary-soft)
  - текущий (последний) сегмент: основной мягкий текст (`text-soft`), начертание **600**
- кликабельные сегменты: `font-weight: 600`, подчёркивание при **hover**
- снизу у блока крошек: отступ до следующего элемента карточки (например, **20px**), чтобы визуально отделить путь от формы, таблицы, списка ссылок и т.д.

---

# 8. Техническая реализация (Frontend)

## 8.1 Компонент

- общий React-компонент **`Breadcrumbs`** (например, `src/components/Breadcrumbs.tsx`)
- формирование цепочки: **`buildBreadcrumbsFromPathname(pathname)`** в `src/utils/breadcrumbLabels.ts` (или аналог)

## 8.2 Подключение

- компонент **подключается на уровне страниц** (и при необходимости в вложенных маршрутах с той же карточкой), **первой строкой внутри** `auth-card`, а **не** единожды в `AppLayout` вместе с `Header` и `Outlet`
- `AppLayout` содержит только шапку и `Outlet` для контента

## 8.3 Пример вёрстки страницы

**Главная** (`/home`):

```jsx
<main className="page page--center">
  <section className="auth-card home-card">
    <Breadcrumbs />
    { /* далее контент: список разделов и т.д. — без h1, название в последней крошке */ }
  </section>
</main>
```

Другая внутренняя страница (тот же принцип: крошки первыми в `auth-card`):

```jsx
<main className="page page--center">
  <section className="auth-card dict-hub-card">
    <Breadcrumbs />
    { /* контент: таблица, кнопки, форма — без дублирующего h1 */ }
  </section>
</main>
```

## 8.4 Стили

- CSS-классы: `breadcrumbs`, `breadcrumbs__list`, `breadcrumbs__item`, `breadcrumbs__link`, `breadcrumbs__current`, `breadcrumbs__sep` (см. `src/style.css`)

---

# 9. Безопасность и источник данных

- крошки — только отображение; кликабельные ссылки ведут на маршруты приложения; **фактические права** по-прежнему проверяет backend; при 403 — отдельная страница/состояние, при этом путь в URL и крошки могут отражать запрошенный маршрут
