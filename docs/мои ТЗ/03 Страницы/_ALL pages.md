# # СТРАНИЦА: ГЛАВНАЯ

---

# 1. Цель
Реализовать главную страницу приложения.

Страница предназначена для:
\- навигации по основным модулям системы
\- отображения доступных разделов в зависимости от роли пользователя

---

# 2. Доступ

- доступ к странице для всех авторизованных пользователей
- для неавторизованных пользователей: → редирект на /auth

---

# 3. Маршрут

/home

---

# 4. UI структура страницы

## 4.1 Общая структура

Страница должна содержать (сверху вниз внутри стеклянной карточки):

- Хлебные крошки (см. п. 4.2) — **название страницы** в UI задаётся только последним сегментом крошек (**«Главная»**), отдельный заголовок (h1) **не** выводится
- Список навигационных элементов

---

## 4.2 Хлебные крошки

- Реализуются **общим компонентом** `Breadcrumbs` (см. ТЗ `02 Глобальные компоненты / # Хлебные крошки.md`); путь **автоматически** строится по текущему URL (`/home`), **та же логика**, что и на остальных внутренних страницах (`buildBreadcrumbsFromPathname` + маппинг сегментов).
- **Размещение:** первый блок **внутри** стеклянной карточки (`auth-card`), над остальным контентом страницы.
- **Внешний вид:** разделитель «/» с **пробелами с обеих сторон**; цвета и отступы — по глобальному ТЗ о крошках.
- **Текстовая цепочка** для маршрута `/home` (один пункт — текущая страница, не ссылка): **Главная**

---

## 4.3 Список навигации

Отображается в виде списка

---

### Элементы

1. Справочники
   - текст: "Справочники"
   - доступ: только admin
   - переход: /dictionaries
2. Учет товаров
   - текст: "Учет товаров"
   - доступ: admin, manager
   - переход: /inventory (заглушка)

---

## 4.4 Отображение по ролям

- admin: видит все пункты
- manager: видит только "Учет товаров"
- user: не видит ни одного пункта

## 4.5 Пустое состояние

Если нет доступных разделов, то отобразить сообщение: "Нет доступных разделов"

---

## 5. Поведение

## 5.1 Загрузка страницы

- определяется роль пользователя
- отображаются только доступные разделы

---

## 5.2 Переходы

При клике:

- Справочники → /dictionaries
- Учет товаров → /inventory

---

# 6. UI требования

- элементы расположены по центру экрана
- ограничение ширины (max-width)
- вертикальный список
- адаптивность (mobile-friendly)
- hover-эффект для элементов
- отступы между элементами

---

# 7. Ограничения

- не использовать таблицы
- не использовать модальные окна
- страница выполняет только навигационную функцию

# 8. Безопасность

- backend проверяет авторизацию
- frontend не является источником прав доступа
  - при попытке доступа к недоступному разделу: → backend возвращает 403

# **DICTIONARY: PRODUCTS (Товары)**

------

# 1. Цель

Реализовать справочник товаров с поддержкой:

- вариативных товаров (цвет / размер / габариты)
- массового создания вариантов
- фильтрации и сортировки
- редактирования

------

# 2. Архитектура модели

Справочник состоит из двух сущностей:

- Product (базовый товар)
- ProductVariant (вариации товара)

------

## 2.1 Product

```
{
  id: string

  name: string
  type_id: string
  sku_base: string

  client_id: string

  is_active: boolean

  created_at: datetime
  created_by: string

  updated_at: datetime
  updated_by: string
}
```

------

## 2.2 ProductVariant

```
{
  id: string

  product_id: string

  color_id: string
  size_id: string | null

  length: number | null
  width: number | null
  height: number | null

  sku: string

  images: string[]

  is_active: boolean
}
```

------

# 3. Зависимости

Использует справочники:

- Product Types
- Clients
- Colors
- Sizes

# **SYSTEM: Product Variant Create Strategy**

---

# 1. Цель

Определить единый механизм генерации вариантов товара (SKU) при создании.

---

# 2. Концепция

Варианты создаются автоматически на основе комбинации:

- цветов
- габаритов
- размеров (опционально)

---

## Формула:

variants = colors × (dimension → sizes mapping)

---

# 3. Входные данные (Create Form)

---

## 3.1 Общие поля

- name
- type_id
- sku (базовый)
- client_id

---

## 3.2 Цвета

colors: color_id[]

- множественный выбор
- только активные значения

---

## 3.3 Габариты

---

### Для техники:

dimensions: [
 { length, width, height }
 ]

---

### Для одежды:

dimension_size_map: [
 {
 dimension: { length, width, height },
 size_ids: string[]
 }
 ]

---

# 4. Алгоритм генерации

---

## 4.1 Для техники

variants = colors × dimensions

---

### Пример:

- colors = 3
- dimensions = 1

→ variants = 3

---

## 4.2 Для одежды

variants = colors × sizes

(где размеры привязаны к габаритам)

---

### Пример:

- colors = 8
- sizes = 9
- dimensions = 3 (группы размеров)

→ variants = 8 × 9 = 72

---

# 5. Псевдокод

variants = []

for color in colors:
 for group in dimension_size_map:
 for size in group.size_ids:
 variants.push({
 color_id: color,
 dimension: group.dimension,
 size_id: size
 })

---

# 6. SKU генерация

---

## Формула:

sku_variant = base_sku + "-" + color_code + "-" + size_code

---

## Пример:

TSHIRT-RED-M
 TSHIRT-BLUE-L

---

## ВАЖНО:

- SKU варианта уникален
- base sku используется как префикс

---

# 7. Фото

---

## Логика:

- фото НЕ участвуют в генерации
- добавляются позже (или копируются)

---

# 8. Поведение при создании

---

## UI:

Пользователь:

1. заполняет форму
2. выбирает:
   - цвета
   - габариты / размеры

---

## При нажатии "Создать":

1. выполняется POST /products
2. backend:
   - создаёт product
   - генерирует variants
   - сохраняет variants

---

# 9. Валидация

---

## Проверяется:

- есть хотя бы 1 цвет
- есть хотя бы 1 dimension
- для одежды:
  - есть size_ids

---

# 10. Ограничения

---

- нельзя создавать товар без вариантов
- нельзя создавать пустые комбинации
- нельзя дублировать комбинации
