# ТЗ: Личный кабинет клиента — Фаза 1 (только чтение)

Дата: 11.06.2026. Документ заменяет `docs/мои ТЗ/06 Процессы/ЛК клиента.md` в части состава разделов и маршрутов. Основан на бизнес-анализе данных системы (поступления, отгрузки, двухосевые остатки, журналы операций, рейсы, магазины клиента).

## 0. Принятые решения

| № | Вопрос | Решение |
|---|---|---|
| 1 | Логистические затраты (`logistics_cost`, стоимости рейсов) | Скрываем полностью |
| 2 | Приоритет отгрузки (`priority_rank`) | Внутренняя очередь, не показываем |
| 3 | Причины брака | Причин и комментариев в данных сейчас нет — историю брака не делаем, показываем только текущий брак и возвраты |
| 4 | Черновики (`draft`) | Клиент не видит ни в списках, ни в детали (404) |

------

# 1. Цель и рамки

Фаза 1 — кабинет «только чтение» поверх существующих данных. Никаких мутаций: все новые эндпоинты — `GET`.

Разделы (меню клиента):

1. Сводка — `/cabinet`
2. Остатки — `/cabinet/balances` (существует, доработка)
3. Поступления — `/cabinet/receipts` (заменяет заглушку)
4. Отгрузки — `/cabinet/shipments` (заменяет заглушку)
5. Брак — `/cabinet/defects`
6. Мои товары — `/cabinet/products` (существует, без изменений)
7. Отчёты — `/cabinet/reports`
8. Профиль и магазины — `/cabinet/profile`

Вне рамок Фазы 1 (Фаза 2): заявки клиента на поставку/отгрузку, загрузка этикеток клиентом, email-уведомления, экспорт файлов, отчёт «движение за период» (требует остатков на дату — помечено нереализованным), неликвиды, управление магазинами.

------

# 2. Доступ и безопасность

- Роль `client`, привязка через `client_id` пользователя. Используется существующая зависимость `_get_current_client_id` в `backend/modules/cabinet/router.py` (роль ≠ client → 403; нет `client_id` → 403 «Обратитесь к администратору для активации доступа»).
- `client_id` **никогда** не принимается с фронта — только из сессии.
- Документ чужого клиента и документ в `draft` → **404** (не 403 — не раскрывать факт существования).
- В ответах кабинета не должно быть: email/идентификаторов сотрудников, внутренних зон/мест, затрат, приоритетов, ссылок на рейсы (см. §4).
- Известное ограничение (зафиксировать, не чинить в этой фазе): `/uploads` смонтирован как статика без авторизации (`app.py`), файлы доступны по прямой ссылке любому, кто знает имя. Показ URL файлов клиенту дыру не расширяет.

# 3. Видимость статусов и журналов

## 3.1 Константы в `config.py`

```python
CABINET_RECEIPT_VISIBLE_STATUSES = frozenset({
    RECEIPT_STATUS_PLANNED, RECEIPT_STATUS_ON_INTAKE, RECEIPT_STATUS_ON_REVIEW,
    RECEIPT_STATUS_DONE, RECEIPT_STATUS_CANCELLED,
})
CABINET_SHIPMENT_VISIBLE_STATUSES = frozenset({
    SHIPMENT_STATUS_PACKING, SHIPMENT_STATUS_ON_PACKING, SHIPMENT_STATUS_RELOCATING,
    SHIPMENT_STATUS_AWAITING_TRIP, SHIPMENT_STATUS_SHIPPED, SHIPMENT_STATUS_CANCELLED,
})
CABINET_RECEIPT_OPS_VISIBLE = frozenset({
    RECEIPT_OP_INTAKE_START, RECEIPT_OP_ARRIVAL_ACCEPT, RECEIPT_OP_ARRIVAL_FIX,
    RECEIPT_OP_CANCEL,
})
CABINET_SHIPMENT_OPS_VISIBLE = frozenset({
    SHIPMENT_OP_PACK, SHIPMENT_OP_PACK_CORRECTION, "cancel",
})
```

## 3.2 Правила журналов

- В кабинет попадают только операции из белых списков. Комментарии у них уже человекочитаемые русские («Принят: 480 шт. (…)», «Упаковка годный (2026-06-10): +200 шт — …»).
- `advance` **не показывается**: его комментарии содержат внутренние коды статусов («packing → on_packing»). Переходы клиент видит по текущему статусу документа и датам (`actual_arrival_date`, `actual_ship_date`).
- Поля `created_by` / `created_by_email` в ответы кабинета не включаются.

# 5. Backend — новые эндпоинты

Всё в `backend/modules/cabinet/` (router / service / schemas) по существующему паттерну. Сервисные функции принимают `connection` первым параметром. Где возможно — переиспользовать доменные сервисы (`list_receipts_aggregated`, `packing_productivity`, расчёт остатков из `balances/service.py`) с принудительным `client_id`; проекция полей — через cabinet-модели в `response_model`. Фильтрация журналов и статусов — обязательно на сервере (не полагаться только на `response_model`).

## 5.1 GET `/cabinet/summary` — сводка для дашборда

Ответ `CabinetSummaryResponse`:

```python
class CabinetBalanceTotals(BaseModel):
    storage_good: int      # доступно к отгрузке
    packing_good: int
    ready_good: int
    total_good: int
    defect_total: int      # брак по всем корзинам

class CabinetEventItem(BaseModel):
    doc_kind: str          # 'receipt' | 'shipment'
    doc_id: str
    doc_number: str
    op_type: str
    qty: int | None = None
    comment: str | None = None
    created_at: str

class CabinetSummaryResponse(BaseModel):
    totals: CabinetBalanceTotals
    active_receipts: list[CabinetReceiptListItem]    # max 5
    active_shipments: list[CabinetShipmentListItem]  # max 5
    events: list[CabinetEventItem]                   # max 10
```

- `totals` — агрегат расчёта остатков по клиенту (эталон в `balances/service.py`).
- `active_receipts` — статусы `planned|on_intake`, сортировка по `arrival_date` ASC (NULL в конец).
- `active_shipments` — статусы `packing|on_packing|relocating|awaiting_trip`, сортировка по `ship_date` ASC.
- `events` — UNION `receipt_ops` + `shipment_ops` (JOIN на документы для `doc_number` и фильтра `client_id`), только белые списки §3.1, `ORDER BY created_at DESC LIMIT 10`.

## 5.2 GET `/cabinet/receipts` — список поступлений

Параметры: `page` (1), `limit` (20, ≤100), `status` (опц., только из visible-набора, иначе 400), `search` (по номеру), `date_from`/`date_to` (по `arrival_date`).

`CabinetReceiptListItem`: `id, doc_number, arrival_date, actual_arrival_date, status, sku_count, total_planned, total_accepted_qty, created_at`.

Всегда принудительно: `client_id` из сессии + `status IN CABINET_RECEIPT_VISIBLE_STATUSES`.

## 5.3 GET `/cabinet/receipts/lines` — поступления «по товарам»

По образцу `/receipts/lines` с теми же фильтрами, что §5.2, плюс `search` по товару/SKU.

`CabinetReceiptLineItem`: `doc_id, doc_number, status, arrival_date, actual_arrival_date, product_name, product_sku, color_name, size_name, planned_qty, accepted_qty`. Без `storage_zone_name`.

## 5.4 GET `/cabinet/receipts/{doc_id}` — деталь поступления

404, если документ не этого клиента, удалён или в `draft`.

```python
class CabinetReceiptDetailResponse(BaseModel):
    doc: CabinetReceiptDoc       # id, doc_number, arrival_date,
                                 # actual_arrival_date, ttn, status, created_at
    lines: list[CabinetReceiptLine]  # product_name, product_sku, color_name,
                                     # size_name, planned_qty, accepted_qty
    ops: list[CabinetOpItem]     # op_type, qty, comment, created_at — только белый список
    totals: dict                 # total_planned, total_accepted
```

Расхождение (`accepted < planned`) фронт считает по строкам — отдельного поля не нужно.

## 5.5 GET `/cabinet/shipments` — список отгрузок

Параметры: `page`, `limit`, `status` (из visible-набора), `cargo_type` (`good|defect`), `search` (номер/магазин строк), `date_from`/`date_to` (по `ship_date`).

`CabinetShipmentListItem`: `id, doc_number, cargo_type, store_names (distinct магазины строк), carrier, ship_date, actual_ship_date, status, sku_count, total_qty, total_packed_qty, total_shipped_qty, created_at`.

## 5.6 GET `/cabinet/shipments/lines` — отгрузки «по товарам»

`CabinetShipmentLineItem`: `doc_id, doc_number, cargo_type, status, ship_date, product_name, product_sku, color_name, size_name, qty, shipped_qty, store_name`.

## 5.7 GET `/cabinet/shipments/{doc_id}` — деталь отгрузки

404 по тем же правилам (чужой / удалён / `draft`).

```python
class CabinetShipmentDetailResponse(BaseModel):
    doc: CabinetShipmentDoc      # id, doc_number, cargo_type, carrier,
                                 # ship_date, actual_ship_date, status, created_at
    lines: list[CabinetShipmentLine]
    ops: list[CabinetOpItem]

class CabinetShipmentLine(BaseModel):
    id: str
    product_name: str
    product_sku: str
    color_name: str | None
    size_name: str | None
    qty: int
    shipped_qty: int
    packed_good: int
    packed_defect: int
    store_name: str | None
    files: list[CabinetLineFile]   # filename, url
```

Без `placements`, `storage_zone_*`, `available_for_pack`, `store_id`.

## 5.8 GET `/cabinet/reports/packing` — отчёт «Упаковка по дням»

Параметры: `date_from`, `date_to` (дефолт — последние 30 дней), `search`.

Переиспользовать `packing_productivity(connection, ...)` из `modules/shipments/service.py` с принудительным `client_id`. Ответ — cabinet-модель той же формы, но строки без `client_id`/`client_name`:

```python
days: list[{packed_date, good, defect, total, sku_count, doc_count,
            rows: [{product_sku, product_name, good, defect, total}]}]
total_good: int
total_defect: int
total: int
```

## 5.9 GET `/cabinet/profile` — профиль и магазины

```python
class CabinetProfileResponse(BaseModel):
    client: dict                  # id, name
    stores: list[dict]            # id, name, is_active
```

Источник: `clients` + `client_stores` (`COALESCE(is_deleted,0)=0`), сортировка магазинов по имени.

## 5.10 Раздел «Брак» — без новых эндпоинтов

- Текущий брак: существующий `GET /cabinet/balances?has_defect=true`.
- Возвраты: `GET /cabinet/shipments?cargo_type=defect` (§5.5).

## 7.3 Наполнение экранов

**Сводка**: 4 KPI-плитки из `totals` (годный на складе = `total_good`; доступно к отгрузке = `storage_good`; в упаковке и готово = `packing_good + ready_good`; брак = `defect_total`), блок «Сейчас в работе» (active_receipts + active_shipments с клиентскими статусами и прогрессом), блок «Последние события» (events: дата + comment).

**Поступления**: таблица `doc_number (mono), supplier_name, arrival_date план/факт, статус-бейдж, total_accepted/total_planned`; строка с расхождением (`done` и принято < плана) подсвечивается `var(--c-warning)`. Верхние табы «По документам / По товарам» (как в основных списках). Фильтры: статус (опции из клиентских лейблов), период, поиск. URL-state через `useFilterParam`/`usePageParam`.

**Деталь поступления**: шапка (номер, статус, поставщик, даты план/факт, ТТН), таблица строк план/факт с подсветкой расхождений, лента операций (только comment + дата, без исполнителей).

**Отгрузки**: таблица `doc_number, направление/магазины, cargo_type-бейдж («Возврат брака» для defect), ship_date план/факт, статус, прогресс упаковано/план/отгружено`. Табы «По документам / По товарам». Фильтры: статус, тип груза, период, поиск.

**Деталь отгрузки**: шапка (номер, тип груза, назначение, перевозчик, даты), таблица строк: товар, магазин (`store_name`), план `qty`, упаковано годный/брак, отгружено; файлы строк — ссылки (`<a href={url}>` filename); лента операций.

**Брак**: таб «Остатки брака» — `getCabinetBalances({has_defect: true})`, колонки: SKU, на хранении (брак), в упаковке (брак), готов к отгрузке (брак), итого брак; таб «Возвраты» — список отгрузок `cargo_type=defect` с defect-лейблами статусов.

**Отчёты**: один отчёт «Упаковка по дням»: фильтр-период (дефолт 30 дней), итоговые KPI (good/defect/total), таблица по дням с раскрытием строк по SKU (по образцу `PackingProductivityView`).

**Профиль и магазины**: карточка клиента (название) + таблица магазинов (название, активность). Только чтение.

# 9. Критерии приёмки

- Клиент после логина попадает в `/cabinet` (существующий `postLoginRedirect`) и видит 8 разделов меню.
- Все данные — только его `client_id`; чужое недоступно ни списком, ни прямой ссылкой.
- Ни на одном экране кабинета нет: затрат, приоритетов, зон/мест склада, номеров рейсов, имён сотрудников, внутренних статус-кодов.
- Статусы везде в клиентской лексике (§6), драфты не видны.
- Заглушка «Раздел временно отключен» удалена.
