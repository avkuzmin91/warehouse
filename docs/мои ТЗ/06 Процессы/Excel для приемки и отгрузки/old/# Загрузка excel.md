# ТЗ: Массовая загрузка движений (поступления и отгрузки) через Excel

------

# 1. Цель

Реализовать единый механизм загрузки:

- поступлений (приход)
- отгрузок (расход)

с поддержкой:

- планирования
- фиксации факта
- корректного влияния на остатки
- строгой валидации

------

# 2. Общая модель

Вводится единая логика:

**Движение товара (Movement)**

Тип движения:

- Поступление
- Отгрузка

------

# 3. Статусы

## Для поступлений:

- Ожидает поступления
- Принят

## Для отгрузок:

- Ожидает отгрузки
- Отгружен

------

# 4. Ключевое правило остатков

В остатки попадают только записи со статусом accepted

------

### Влияние:

| Тип         | Влияние   |
| ----------- | --------- |
| Поступление | + остаток |
| Отгрузка    | - остаток |
| любой       | не влияет |

------

# 5. Формат Excel

Лист: movements

| Колонка  | Обязательность                              | Описание        |
| -------- | ------------------------------------------- | --------------- |
| date     | да                                          | дата операции   |
| клиент   | да                                          | клиент          |
| name     | да                                          | название товара |
| barcode  | да                                          | штрих-код       |
| color    | да                                          | цвет            |
| size     | условно: да - для одежды, нет - для техники | размер          |
| quantity | да                                          | количество      |
| status   | да                                          | статус          |
| comment  | нет                                         | комментарий     |

------

------

# 7. Валидация

## 7.1 Общие проверки

- файл читается
- есть лист movements
- есть все обязательные колонки

------

## 7.2 Проверка строки

------

### Дата:

- обязательна
- если status = accepted:
  - дата ≤ текущей

------

### Штрих-код:

- обязателен
- должен существовать в списке товаров

------

### Поиск варианта

Одежда:

- barcode + color + size

Техника:

- barcode + color

------

Если не найден:

- ошибка "Товар не найден"

------

### Количество:

- ≥ 1, целое число

------

### Атрибуты:

Одежда:

- color обязателен
- size обязателен

------

### Дополнительно для outgoing:

- если status = accepted:
  - проверить остаток
  - нельзя списать больше доступного

------

# 8. Предпросмотр

```

  "valid_rows": [...],

    {
      "row": 10,
      "error": "Недостаточно остатка"
    }
  ]
}
```

------

# 9. Создание записей

Для каждой валидной строки:

------

## incoming:

| результат           |
| ------------------- |
| Ожидает поступления |
| Принят              |

------

## outgoing:

| результат        |
| ---------------- |
| Ожидает отгрузки |
| Отгружен         |

------

# 10. Влияние на остатки

- приемка → увеличить
- отгрузка → уменьшить
- Ожидает приемки / отгрузки → не влияет

------

# 11. Клиент

- НЕ передаётся в Excel
- определяется системой по штрих-коду

------

# 12. Логирование

Сохранять:

- user_id
- дата
- файл
- успешные строки
- ошибки

------

# 13. API

POST /import/movements/preview

POST /import/movements/commit

------

# 14. Ограничения

- нельзя пропустить валидацию
- нельзя создать запись без товара
- нельзя уйти в минус

------

# 15. UI: кнопка загрузки Excel

## Требование

В панели фильтров добавить иконку загрузки Excel:

Расположение:

- левее иконки "Создать"

------

## Поведение:

При нажатии:

1. Открывается модальное окно
2. Доступны действия:
   - скачать шаблон
   - загрузить файл
3. После загрузки:
   - показать предпросмотр
4. Кнопка:
   - "Подтвердить загрузку"

------

## Название кнопки:

- "Импорт Excel"

------

## Иконка:

- иконка загрузки файла (upload)

------

# 16. UX сценарий

1. Пользователь нажимает "Импорт Excel"
2. Загружает файл
3. Видит ошибки
4. Исправляет или подтверждает
5. Система создаёт движения

# Контрольные процедуры и сверка с объектами системы

------

# 18. Общий принцип контроля

Excel НЕ является источником истины.
 Все данные должны быть **жёстко сверены со справочниками системы**.

Загрузка = не просто создание записей, а:

**сопоставление + валидация + контроль целостности**

------

# 19. Сверка с товарами (критично)

## 19.1 Поиск товара

Поиск выполняется строго:

Одежда:

- barcode + color + size

Техника:

- barcode + color (если есть)

------

## 19.2 Контроль существования

Если товар НЕ найден:

- строка помечается как ошибка
- создание записи запрещено

Ошибка:
 "Товар не найден в системе"

------

## 19.3 Контроль уникальности варианта

Если найдено более 1 варианта:

- ошибка:
   "Найдено несколько вариантов товара"

------

## 19.4 Контроль принадлежности

Если используется модель "товары клиента":

- проверять:
  - товар принадлежит клиенту

Если нет:

- ошибка:
   "Товар не привязан к клиенту"

------

# 20. Сверка атрибутов

## Цвет:

- должен существовать в справочнике цветов
- должен быть доступен для товара

------

## Размер:

- должен существовать в справочнике размеров
- должен быть допустим для товара

------

## Ошибки:

- "Недопустимый цвет"
- "Недопустимый размер"

------

# 21. Контроль остатков (для отгрузки)

## При status = accepted:

Перед созданием:

- рассчитать текущий доступный остаток

------

## Проверка:

```
остаток >= quantity
```

------

## Если нет:

- ошибка:
   "Недостаточно остатка"

------

## Важно:

Проверка должна учитывать:

- уже загружаемые строки (в рамках одного файла)
- порядок выполнения

------

# 22. Контроль дубликатов

## 22.1 Внутри файла

Проверять строки с одинаковыми:

- operation_type
- date
- barcode
- color
- size

------

Если совпадают:

- warning:
   "Возможный дубликат"

------

## 22.2 В системе

Проверять:

- была ли уже такая операция

(опционально, если нет ID)

------

# 23. Контроль статусов

## Проверка значения:

Допустимые:

- planned
- accepted

------

Если другое значение:

- ошибка:
   "Недопустимый статус"

------

# 24. Контроль даты

## Для accepted:

- дата ≤ текущей

------

## Для planned:

- любая дата допустима

------

## Ошибки:

- "Дата в будущем недопустима для подтверждённой операции"

------

# 25. Контроль целостности перед записью

Перед commit:

Система должна гарантировать:

- все строки валидны (или выбран режим partial)
- нет нарушений остатков
- все товары существуют
- все атрибуты корректны

------

# 26. Контроль атомарности

## Режим 1 (строгий):

- если есть ошибки → ничего не загружается

## Режим 2 (partial):

- валидные строки → загружаются
- невалидные → отклоняются

------

# 27. Контроль после загрузки (post-check)

После commit:

Система должна:

- пересчитать остатки
- проверить:
  - нет отрицательных значений
  - нет аномалий

------

## Если ошибка:

- откат транзакции

------

# 28. Аудит

Для каждой строки сохранять:

- исходные данные из Excel
- результат обработки
- ошибки (если были)

------

# 29. Отчёт по загрузке

После завершения:

```
{
  "total": 100,
  "success": 92,
  "failed": 8,
  "warnings": 5
}
```

------

# 30. UX-контроль

В предпросмотре обязательно:

- показывать:
  - найденный товар (название, фото)
  - клиент
  - статус
- выделять:
  - ошибки (красный)
  - предупреждения (жёлтый)

------

# 31. Защита от “тихих ошибок”

Запрещено:

- автоматически создавать товары
- автоматически создавать цвета/размеры
- “догадываться” значения

------

# 32. Ключевой принцип

Система должна быть:

- строгой к данным
- предсказуемой
- прозрачной
