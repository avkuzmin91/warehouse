# Логика поступлений с планированием

------

## 1. Цель

Обеспечить учёт **поступлений на склад** с возможностью:

- планирования поступлений
- фиксации фактического поступления
- контроля влияния на складские остатки

------

## 2. Сущность: Поступление

В системе фиксируется единая сущность — **Поступление**.

Каждая запись содержит:

- товар и его вариант
- количество
- дату поступления
- комментарий
- статус

------

## 3. Статусы

**Фиксированный набор:**

- **Ожидает поступления**
- **Принят**

------

### Правила:

- При создании записи:
  → статус = **Ожидает поступления**
- При подтверждении:
  → статус = **Принят**

------

## 4. Ключевое правило остатков

❗ В складские остатки попадают **только поступления со статусом “Принят”**

- “Ожидает поступления” не влияет на остатки
- при смене статуса выполняется пересчёт остатков

------

## 5. Логика товара и поиска варианта

Полностью соответствует основной логике системы:

### Обязательные поля:

- Дата поступления (≤ текущей даты для статуса Принят)
- Штрих-код
- Цвет
- Размер (если требуется типом товара)

------

### Правила поиска:

- Одежда → штрих-код + цвет + размер
- Техника → штрих-код + цвет

------

### Результат:

**Если вариант найден:**

- отображается информационный блок товара

**Если не найден:**

- сообщение «Товар не найден»
- сохранение невозможно

------

## 6. Создание поступления

### 6.1 Поля формы

1. Дата
2. Штрих-код
3. Цвет
4. Размер (если требуется)
5. Количество (≥ 1)
6. Комментарий (необязательно)

- блок найденного товара

------

### 6.2 Действия

- **Запланировать поступление**
  - статус = **Ожидает поступления**
  - не влияет на остатки
- **Принять на склад**
  - статус = **Принят**
  - влияет на остатки
- **Отмена**
  - выход без сохранения

------

### Требования к кнопке планирования:

Название должно явно объяснять действие:

✅ «Запланировать поступление»

⚠️ Пользователь должен понимать:

- запись не попадёт в остатки
- это предварительное состояние

------

## 7. Редактирование

### Важно:

Редактирование доступно **на всех статусах**

------

### Поведение:

- можно изменять все поля
- при изменении товара выполняется повторный поиск варианта
- изменения сохраняются независимо от статуса

------

## 8. Финализация

### Действие:

- **Принять на склад**

### Условия:

- найден вариант товара
- заполнены обязательные поля
- количество ≥ 1

### Результат:

- статус: Ожидает поступления → Принят
- обновляются складские остатки

------

---

### 9.3 Просроченные поступления (NEW)

Добавить визуальную логику просрочки.

------

### Условие просрочки:

Поступление считается **просроченным**, если:

```
status = "Ожидает поступления"
AND
date < today
```

------

### Визуальное отображение:

- строка таблицы подсвечивается **красным цветом**
- статус остаётся: **Ожидает поступления** (НЕ меняется)

------

### Приоритет цветов:

| Условие                 | Цвет      |
| ----------------------- | --------- |
| Принят                  | зелёный   |
| Ожидает (date >= today) | жёлтый    |
| Ожидает (date < today)  | 🔴 красный |

------

### UX-требования:

- красный цвет должен быть:
  - заметным, но не агрессивным
  - не ломать читаемость текста
- возможно добавить:
  - иконку ⚠
  - tooltip: "Просроченное поступление"

------

## ➕ ДОБАВИТЬ В РАЗДЕЛ 11 (UX-логика)

### Просрочка

Система должна визуально сигнализировать:

- что поступление не было выполнено вовремя
- требуется действие пользователя

------

### Поведение пользователя:

Пользователь может:

- отредактировать дату
- принять поступление
- оставить как есть (осознанно)

------

## ➕ ДОБАВИТЬ В ОГРАНИЧЕНИЯ

```
- просрочка определяется только на frontend уровне
- не создаётся отдельный статус "Просрочен"
```

------

### 9.3 Фильтры

- Статус:
  - Ожидает поступления
  - Принят

Остальные фильтры без изменений.

------

## 10. Ограничения и правила

- нельзя создать запись без найденного варианта товара
- все записи структурно валидны
- количество ≥ 1
- дата ≤ текущей
- остатки обновляются только по “Принят”
- редактирование доступно всегда

------

## 11. UX-логика

### Сценарий:

1. Пользователь создаёт поступление
2. Выбирает:
   - «Запланировать поступление»
   - или «Принять на склад»
3. При необходимости редактирует в любой момент

------

### Смысл статусов:

- **Ожидает поступления** → планирование
- **Принят** → факт прихода на склад

------

## 12. Согласованность интерфейса

- единые паттерны форм и таблиц
- одинаковая логика статусов
- консистентные действия пользователя

------

## 13. Резюме

Модель:

→ Ожидает поступления → Принят

Даёт:

- простую бизнес-модель без лишних сущностей
- прозрачный учёт остатков
- поддержку планирования без усложнения системы
