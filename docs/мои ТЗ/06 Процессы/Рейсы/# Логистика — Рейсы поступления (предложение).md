# Логистика: Рейсы поступления — предложение по доработке

Документ-предложение: новые сущности **Рейс** и **Мои задачи**, раздел меню
**Логистика**, и то, как они стыкуютс я с уже реализованными **Поступлениями**.

Статус документа: черновик к обсуждению. Архитектура подгоняется под текущие
паттерны проекта (append-only журнал, статусные переходы, слои фронта) — см.
[CLAUDE.md](../../../../CLAUDE.md). Спорные места вынесены в раздел
[«Открытые вопросы»](#12-открытые-вопросы).

---

## 1. Краткая идея

Сегодня поступление (`receipt_docs`) живёт само по себе: у него есть
`logistics_cost`, но нет понятия «машина приехала», «кто вёз», «сколько ждали
разгрузку». Вся транспортная часть не учитывается.

Вводим **Рейс** — это одна физическая поездка машины на склад. К рейсу
привязывается одно или несколько поступлений (возможно, от разных клиентов).
Рейс ведёт **транспортную** часть (откуда, кто везёт, кузов, время, стоимость),
а поступление — **товарную** (что и сколько приехало). Они связаны, но не дублируют
друг друга.

Поверх этого — раздел **«Мои задачи»** на Главной: единая очередь того, что
именно сейчас ждёт от текущего пользователя (менеджера или кладовщика).

## 2. Сущности

### 2.1 Рейс (`trip_*`)

Предлагаю сразу заложить **единую** сущность «Рейс» с направлением
`direction = inbound | outbound`, но **реализовать только `inbound`**
(рейс поступления). Тогда позже отгрузочные рейсы лягут в ту же модель без
переписывания. Названия статусов выбираю нейтральными к направлению.

Таблицы (по аналогии с `receipt_docs / receipt_lines / receipt_ops`):

| Таблица | Назначение |
|---|---|
| `trip_docs` | шапка рейса: транспорт, время, стоимость, статус |
| `trip_lines` | привязка поступлений к рейсу (рейс ↔ много поступлений) |
| `trip_ops` | **append-only** журнал всех изменений рейса |

> Журнал `trip_ops` — как `receipt_ops`: каждое значимое действие (создание,
> привязка поступления, отметка прибытия, перевод ответственного, внесение
> факта) пишет новую строку с `op_type` и русским `comment`
> (`"Прибытие: 14:20"`, `"Логистика факт: 12 000 ₽"`). Это даёт полный аудит:
> кто и когда что внёс — критично, потому что рейс ведут два разных человека.

### 2.2 Связь Рейс ↔ Поступление

- `trip_lines (trip_id, receipt_doc_id, client_id, …)` — many-to-one к рейсу.
- Одно поступление принадлежит **не более чем одному рейсу** (рекомендую
  ограничение `UNIQUE(receipt_doc_id)` среди не-аннулированных).
- На карточке поступления показываем бейдж «Рейс TR-00012» со ссылкой.

### 2.3 Мои задачи (вычисляемая, без своей таблицы)

«Мои задачи» — это **не** новая хранимая сущность, а агрегирующее представление
поверх `trip_docs` и `receipt_docs`. Задача = документ, который сейчас находится
в статусе, требующем действия от текущего пользователя/его роли.

Зачем без отдельной таблицы: чтобы не плодить рассинхрон. Источник правды —
статус документа и поле «ответственный». Подробнее — [§7](#7-мои-задачи).

## 3. Поля рейса (`trip_docs`)

Делю поля по тому, **кто и на каком шаге** их заполняет.

### 3.1 Планирование (заполняет менеджер при создании)

| Поле | Тип | UI-название | Примечание |
|---|---|---|---|
| `trip_number` | str | Номер рейса | автогенерация `TR-00001` (как `WH-` у поступлений) |
| `direction` | enum | — | `inbound` (пока единственное значение) |
| `origin` | Выбор из справочника | Откуда | из справочника `warehouses` (склады) |
| `carrier_id` | Выбор из справочника | Перевозчик | ссылка на справочник `carriers` |
| `carrier_name` | str? | — | snapshot названия (как `client_name` в поступлении) |
| `vehicle_type_id` | Выбор из справочника | Тип кузова | новый справочник `vehicle_types` (тент / реф / изотерм / борт); госномер не храним |
| `vehicle_type_name` | str? | — | snapshot названия типа кузова |
| `transport_ordered_at` | datetime | Транспорт заказан | «во сколько заказали транспорт» |
| `eta` | datetime | Плановое прибытие | необязательное, для планирования |
| `cost_estimate` | float | Стоимость логистики (план) | предварительная стоимость рейса |
| `comment` | str | Комментарий | |

### 3.2 Исполнение (заполняет кладовщик)

| Поле | Тип | UI-название | Примечание |
|---|---|---|---|
| `arrived_at` | datetime | Прибытие | фактическое время прибытия машины |
| `unload_finished_at` | datetime | Окончание разгрузки | |
| `load_factor` | enum | Загруженность | `full` (полная) / `partial` (неполная) |

> Производное (не храним, считаем): **длительность разгрузки** =
> `unload_finished_at − arrived_at`. Показываем в карточке и используем потом в
> аналитике «эффективность рейса».

### 3.3 Закрытие (заполняет менеджер)

| Поле | Тип | UI-название | Примечание |
|---|---|---|---|
| `logistics_cost_actual` | float? | Стоимость логистики (факт) | фактическая стоимость перевозки |
| `waiting_cost` | float? | Стоимость простоя | отдельно — оплата ожидания/простоя транспорта |
| `waiting_minutes` | int? | Время простоя, мин | опц.: для расчёта `waiting_cost` |

> **Итоговая стоимость рейса** = `logistics_cost_actual + waiting_cost`.
> Простой держим **отдельной** строкой, а не «зашитым» в факт — этого прямо
> требует ТЗ и это нужно для аналитики (простой = убыток, его хотят видеть
> отдельно от тарифа перевозки).

### 3.4 Системные

`status`, `assignee_role` / `assignee_id` (см. §7), `created_at`, `created_by`,
`updated_at`, `is_deleted`.

## 4. Статусы рейса

Предлагаемый набор (английский код → русское название), стиль — как у
поступлений в [config.py](../../../../backend/config.py):

| Код | UI-название | Кто «владеет» (ответственный) |
|---|---|---|
| `draft` | Черновик | Менеджер (собирает рейс, может прерваться и сохранить) |
| `awaiting_arrival` | Ожидает прибытия | Кладовщик |
| `unloading` | Разгрузка | Кладовщик |
| `costing` | Уточнение стоимости | Менеджер |
| `closed` | Закрыт | — (финал) |
| `cancelled` | Аннулирован | — (финал) |

Переходы (`TRIP_STATUS_TRANSITIONS`):

```
draft ──(менеджер: «Передать на склад»)──▶ awaiting_arrival
awaiting_arrival ──(кладовщик: «Отметить прибытие»)──▶ unloading
unloading ──(кладовщик: «Завершить разгрузку»)──▶ costing
costing ──(менеджер: «Закрыть рейс»)──▶ closed

любой не финальный ──(«Аннулировать»)──▶ cancelled
```

### Комментарии по статусам

- **`draft`** — рейс ещё редактируется менеджером, можно привязывать/отвязывать
  поступления, менять транспорт. Кладовщик его не видит в своей очереди.
- **Объединять ли `awaiting_arrival` и `unloading`?** Можно сделать один статус
  «Ожидает прибытия» и считать «начало разгрузки» по факту `arrived_at`.
  Но отдельный `unloading` полезен кладовщику как явный сигнал «машина здесь,
  идёт разгрузка» и даёт чистую точку для расчёта простоя. Рекомендую оставить
  два — см. [открытый вопрос 12.1](#12-открытые-вопросы).
- **`costing`** (в вашем тексте — «менеджер получает задачу в работу») — назвал
  так, потому что суть шага именно довнесение фактической стоимости. Альтернатива
  — `on_review` (зеркально поступлениям). Готов выровнять под общий словарь.

## 5. Сценарий по шагам (с привязкой к статусам)

### Шаг 1. Менеджер планирует поступление *(уже реализовано)*

Заводит `receipt_docs`: клиент, дата, стоимость для клиента, состав, количество.
Поступление в статусе `planned`. Рейса пока может не быть.

### Шаг 2. Менеджер создаёт рейс (раздел «Логистика»)

- Создаёт `trip_docs` (`draft`), заполняет транспортную часть (§3.1).
- Привязывает существующие поступления (разных клиентов) → `trip_lines`.
- **Если поступления ещё нет** — создаёт его прямо из карточки рейса
  (та же форма, что и обычное создание поступления; на выходе оно сразу
  привязано к рейс, все поступления видно к какому рейсу привязаны).
- Жмёт **«Передать на склад»** → рейс `awaiting_arrival`, ответственный —
  роль кладовщик (их может быть несколько). Рейс появляется в «Моих задачах» кладовщиков.

### Шаг 3. Кладовщик принимает рейс

- Видит рейс в очереди (`awaiting_arrival`).
- Машина приехала → **«Отметить прибытие»**: вносит `arrived_at`,
  рейс → `unloading`.
- После разгрузки → **«Завершить разгрузку»**: вносит `unload_finished_at`,
  `load_factor` (полная/неполная) → рейс `costing`, ответственный — менеджер.
- **В этот момент привязанные поступления переходят `planned → on_intake`**
  (новый статус «На приёмке», см. [§8.3](#83-новый-статус-поступления-на-приёмке-решение))
  и падают кладовщику в работу.
- Кладовщик на статусе «На приёмке» заполняет фактическое количество в колонке
  **«Принято»** по строкам, затем жмёт **«Принять товары»** → поступление
  переходит `on_intake → on_review` («На проверке») — дальше как было.

> Связка: завершение разгрузки рейса = триггер `planned → on_intake` для всех
> привязанных поступлений. Это единственная точка, где рейс **меняет статусы
> поступлений**. Делаем в `service.py` рейса в одной транзакции, с журнальными
> записями и в `trip_ops`, и в `receipt_ops` каждого поступления
> (`"Поступление переведено на приёмку по рейсу TR-00012"`). Кнопку «Принять
> товары» жмёт кладовщик отдельно, по каждому поступлению.

### Шаг 4. Менеджер закрывает рейс

- Получает рейс в работу (`costing`).
- Вносит `logistics_cost_actual` и отдельно `waiting_cost` (простой).
- Может **отредактировать любую транспортную часть** рейса (исправить ошибки
  кладовщика) — на статусе `costing` менеджеру открыты все поля.
- **«Закрыть рейс»** → `closed`. Процесс рейса завершён.

> Подсчёт количества по поступлениям (их перевод `on_review → done`) идёт
> **своим** процессом и не блокирует закрытие рейса. Рейс и поступления
> закрываются независимо. См. [открытый вопрос 12.2](#12-открытые-вопросы).

## 7. «Мои задачи»

Раздел-виджет на Главной (`/home`) + опционально пункт меню. Это **очередь
действий**, собранная из документов, где сейчас ход за текущим пользователем.

### 7.1 Модель ответственного

Добавляем к `trip_docs` (и при желании к `receipt_docs`):

- `assignee_role` — роль-владелец текущего статуса (заполняется автоматически
  при переходе: `awaiting_arrival/unloading → warehouse_manager`,
  `costing → manager`).
- `assignee_id` *(опц.)* — конкретный пользователь, если задачу назначили
  адресно.

Задача попадает «ко мне», если:
`assignee_id == me` **или** (`assignee_id` пуст **и** `assignee_role == моя роль`).

### 7.2 Источники задач (на старте)

| Тип задачи | Источник | Условие |
|---|---|---|
| Встретить рейс | `trip_docs` | `status = awaiting_arrival`, роль кладовщик |
| Завершить разгрузку | `trip_docs` | `status = unloading`, роль кладовщик |
| Уточнить стоимость рейса | `trip_docs` | `status = costing`, роль менеджер |
| Принять товары | `receipt_docs` | `status = on_intake`, роль кладовщик |
| Проверить поступление | `receipt_docs` | `status = on_review` |

### 7.3 Карточка задачи

`{ kind, title, doc_number, link, status, age }`, где `age` — сколько висит
(для подсветки «просрочено», как `isReceiptOverdue`). Сортировка — старые
сверху. Клик → карточка документа.

### 7.4 Реализация

`GET /tasks?scope=mine` — один агрегирующий эндпоинт (read-only, по образцу
`list_receipts_aggregated`: отдельный SQL `UNION ALL` по источникам, **без**
replay журналов). Никакой записи, никакого нового состояния.

## 8. Backend — структура

Новый домен по канону [CLAUDE.md §3](../../../../CLAUDE.md):

```
backend/modules/logistics/
  __init__.py
  router.py      # /trips/*  — эндпоинты, авторизация, валидация переходов
  service.py     # next_trip_number, compute_state, привязка поступлений,

  schemas.py     # TripDoc(Create|Update|Response|ListItem|ListResponse), TripLine*

backend/modules/tasks/
  __init__.py
  router.py      # GET /tasks  (агрегация, read-only)

```

### 8.1 Гард роли кладовщика *(решение)*

Сейчас в [auth/service.py](../../../../backend/modules/auth/service.py) есть только
`get_current_user` / `get_current_manager`. Добавляем третью зависимость:

```python
def get_current_warehouse(user=Depends(get_current_user)):
    # пускает кладовщика и менеджерский состав (admin/manager — надмножество прав)
    ensure_warehouse_staff(user)   # role ∈ {warehouse_manager, manager, admin}
    return user
```

Применение: `arrival` / `unload` — `Depends(get_current_warehouse)`; планирование,
`cost`, `close`, привязки — `Depends(get_current_manager)`.

### 8.2 Новый справочник `vehicle_types` *(решение)*

Тип кузова — справочник. Добавляем `"vehicle_types"` в `DICTIONARY_TABLES`
([config.py](../../../../backend/config.py)) и таблицу-словарь по образцу
`carriers` (миграцией). Госномер не храним.

### 8.3 Новый статус поступления «На приёмке» *(решение)*

Добавляем **новый** статус поступления между `planned` и `on_review`. Это меняет
существующий одношаговый приём (`arrive_receipt` сейчас делает
`planned → on_review` за раз) на двухшаговый:

```
было:  planned ──(заполнить «Принято» + перейти)──▶ on_review
стало: planned ──(товар прибыл)──▶ on_intake ──(«Принять товары»)──▶ on_review
```

**Новый статус:** код `on_intake`, подпись «На приёмке» (параллельно `on_review`
«На проверке»). В [config.py](../../../../backend/config.py):

```python
RECEIPT_STATUS_ON_INTAKE = "on_intake"   # «На приёмке»

# в RECEIPT_STATUS_RU:
RECEIPT_STATUS_ON_INTAKE: "На приёмке",

# RECEIPT_STATUS_TRANSITIONS:
RECEIPT_STATUS_DRAFT:     RECEIPT_STATUS_PLANNED,
RECEIPT_STATUS_PLANNED:   RECEIPT_STATUS_ON_INTAKE,   # было → on_review
RECEIPT_STATUS_ON_INTAKE: RECEIPT_STATUS_ON_REVIEW,   # новый шаг
RECEIPT_STATUS_ON_REVIEW: RECEIPT_STATUS_DONE,
```

**Поведение и переразбивка существующего кода:**

1. **`planned → on_intake` — «Товар прибыл / Начать приёмку».** Два триггера:
   - **авто** — завершение разгрузки рейса (`POST /trips/{id}/unload`) переводит
     все привязанные поступления в `on_intake` в той же транзакции;
   - **вручную** — для поступлений без рейса кладовщик жмёт «Начать приёмку»
     (новый эндпоинт, напр. `POST /receipts/{id}/intake`).
   На этом шаге `accepted_qty` ещё не трогаем.
2. **На статусе `on_intake`** кладовщик правит колонку «Принято» (`accepted_qty`)
   по строкам — редактирование `accepted_qty` уже разрешено на `on_review`,
   добавляем в это правило и `on_intake`
   ([router.py:473](../../../../backend/modules/receipts/router.py)).
3. **`on_intake → on_review` — «Принять товары».** Это **бывший** `arrive_receipt`
   ([router.py:719](../../../../backend/modules/receipts/router.py)): фиксирует
   «Принято» и переводит документ дальше. Меняем его предусловие
   `draft/planned → on_intake`. Дальше (`on_review → done`, QC) — **как было**.

> Колонки строки (`accepted_qty` «Принято», `accepted`, `defect`, `qc_status`)
> не меняются — добавляется только промежуточный статус и его переход.

**Область действия:** новый статус — общий для всех поступлений, не только
рейсовых (см. [§12.2](#122-остаётся-уточнить) — нужно подтвердить, что
поступления без рейса тоже идут через «Начать приёмку», а не напрямую в
`on_review`).

## 10. Предлагаемые улучшения «от себя»

1. **Единая сущность «Рейс» с `direction`.** Сейчас делаем `inbound`, но модель
   и статусы нейтральны — отгрузочные рейсы позже лягут сюда же.
2. **Простой — отдельным полем (`waiting_cost`/`waiting_minutes`).** Не зашивать
   в факт. Это и требование ТЗ, и будущая аналитика «сколько теряем на простоях».
3. **`load_factor` (полная/неполная).** Кроме галочки кладовщика — это метрика
   эффективности: неполные рейсы = переплата за логистику. Стоит копить с первого
   дня.
4. **Производные времена не хранить, а считать** (длительность разгрузки, простой
   от `arrived_at` до `unload_finished_at`) — меньше рассинхрона.
5. **Перевод ответственности — это `op` в журнале (`handoff`).** Тогда «Мои
   задачи» и история «у кого лежал рейс и сколько» получаются бесплатно из
   `trip_ops`.
6. **Терминология статусов поступления.** Раз уж касаемся: в
   [config.py](../../../../backend/config.py) `planned` = «В плане»,
   `on_review` = «На проверке». Предлагаю у рейса держать совместимый словарь
   (`costing` ↔ «Уточнение стоимости») и единый тон бейджей.

## 11. Что НЕ делаем (рамки)

- Не трогаем существующую логику приёмки/QC поступлений, кроме **одного**
  каскадного перехода `planned → on_review` при завершении разгрузки рейса.
- Не строим «универсальную форму документа» и не абстрагируем рейс+поступление
  в общий слой — это два разных домена (правило двух повторений,
  [CLAUDE.md §4](../../../../CLAUDE.md)).
- Не оживляем `/import/*`, `/analytics/*` — аналитика по рейсам отдельной задачей.
- «Мои задачи» — без своей таблицы и без нового состояния.
- **Распределение стоимости рейса по клиентам/поступлениям — пока не делаем.**
  Фактическая стоимость хранится на рейсе целиком; биллинг по клиентам — отдельная
  задача позже.

## 12. Решения и остающиеся вопросы

### 12.1 Зафиксировано

1. **Два статуса разгрузки** — `awaiting_arrival` + `unloading`. ✅
2. **Закрытие рейса независимо от поступлений** — рейс можно перевести в `closed`,
   даже если привязанные поступления ещё `on_review` (не досчитаны). Процессы
   рейса и приёмки не блокируют друг друга. ✅
3. **Гард роли кладовщика** — добавляем `get_current_warehouse` (см. [§8.1](#81-гард-роли-кладовщика-решение)). ✅
4. **Тип кузова** — справочник `vehicle_types` (см. [§8.2](#82-новый-справочник-vehicle_types-решение)); госномер не храним. ✅
5. **Распределение стоимости по клиентам** — в первой версии **не делаем**
   (см. [§11](#11-что-не-делаем-рамки)). ✅
6. **`origin` (Откуда)** — выбор из справочника `warehouses`. ✅

### 12.2 Остаётся уточнить

1. **Адресность задач.** Достаточно ли очереди по роли, или нужна возможность
   назначить рейс конкретному кладовщику (`assignee_id`)? По умолчанию делаю
   очередь по роли, `assignee_id` оставляю как опциональное поле «на вырост».
2. **Номер рейса.** Формат `TR-00001` ок? Сквозной или с префиксом года?
3. **Поступления без рейса.** Новый статус `on_intake` «На приёмке» — общий
   ([§8.3](#83-новый-статус-поступления-на-приёмке-решение)). Для рейсовых вход
   в него автоматический (при разгрузке). Подтвердить: поступления **без** рейса
   тоже проходят через «Начать приёмку» (`planned → on_intake → on_review`), а не
   прыгают сразу в `on_review`? (По умолчанию делаю единый путь через
   `on_intake`.)
