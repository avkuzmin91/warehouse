# План доработок: филиалы и раздельная аналитика

Дата: 30.08.2026
Статус: решения приняты (§1), готово к оформлению ADR и старту этапа 1

Задача бизнеса: открыть второй филиал (Краснодар) со своими сотрудниками, поступлениями,
приёмками, упаковками и отгрузками. Аналитика — раздельная: сотрудник Краснодара не видит
цифры Москвы и наоборот. Управляющий состав видит оба филиала и сводно.

---

## 1. Принятые решения

| # | Вопрос | Решение |
|---|---|---|
| Q1 | Что такое филиал | **Филиал = одна запись справочника «Наши склады»** (`own_warehouses`). Отдельную таблицу `branches` не заводим |
| Q2 | Счёт клиенту | **Счёт на филиал.** Клиент, обслуживаемый обоими, получает два счёта |
| Q3 | Тарифы клиента | **Филиальные сразу, без фолбэка.** Нет цены филиала → услуга не тарифицируется и видна как пробел |
| Q4 | Номенклатура и SKU | **Общие на компанию** |
| Q5 | Межфилиальные перемещения | **Позже, отдельной задачей.** Задел `branch_id` в журнале остатков делается сейчас |
| Q6 | Филиал у расхода | **Обязателен у любого расхода.** По умолчанию подставляется домашний филиал автора. Понятия «общефирменный расход» в системе нет |
| Q7 | Доступ к деньгам | **3 именованные галочки на пользователе** поверх роли + область видимости филиалов. Полную систему прав не делаем |
| Q8 | Ведение филиалов | **Только администратор** — и заведение филиала, и перевод сотрудника |

Факт по данным: в «Наших складах» сейчас **две записи** — два реальных места, но аренда
ведётся одной суммой. Разбивка по площадкам не нужна → миграция сливает их в одну запись
«Москва» с переносом истории ставок аренды.

### Два следствия, которые надо принять осознанно

**1. Справочник «Наши склады» получает двойную нагрузку** — он одновременно физическая
площадка (носитель аренды) и организационная единица (носитель аналитики). Пока каждому
городу соответствует одна запись, это работает. Если завтра в Москве появится вторая
площадка со своей арендой, её нельзя будет завести, не создав второй филиал с отдельной
аналитикой. Это цена решения Q1; фиксируем её в ADR явно, чтобы через год не выяснять
заново.

**2. Реклама, сервер, разработка и бухгалтерия попадут на Москву.** Раз общефирменных
расходов в системе нет (Q6), эти суммы придётся волевым решением вешать на конкретный
город — и P&L Москвы будет систематически хуже краснодарского на всю величину накладных.
Сравнивать филиалы между собой по итоговой прибыли будет некорректно.
**Дешёвая страховка:** завести в справочнике категорий расходов отдельную категорию
«Общефирменные». Схему это не меняет, но даёт возможность в любой момент отфильтровать
такие расходы в отчёте или переразнести их — без миграции и без переписывания истории.
Рекомендую сделать это в этапе 4.

## 2. Требования

| # | Требование | Проверяемый критерий |
|---|---|---|
| R1 | Операционное разделение | Документ, зона, ячейка, остаток, сотрудник, задача принадлежат ровно одному филиалу |
| R2 | Изоляция аналитики | Пользователь с областью «свой филиал» ни на одном эндпоинте не получает данные чужого филиала |
| R3 | Сводный доступ | Есть область «все филиалы»: сводные цифры + разрез «по филиалам» |
| R4 | Обратная совместимость | Существующие данные целиком уезжают в филиал «Москва» без ручной разметки |
| R5 | Fail-closed | Новый эндпоинт, забывший фильтр, ловится тестом, а не продом |

## 3. Модель данных

### 3.1 Филиал

Отдельной таблицы нет. Филиал — запись `own_warehouses`; в остальных таблицах ссылка
называется `branch_id TEXT REFERENCES own_warehouses(id)`.

Имя колонки намеренно `branch_id`, а не `warehouse_id`: `warehouse_rent_rates.warehouse_id`
уже означает «площадка, на которую начисляется аренда», и смешивать два смысла в одном
имени хуже, чем допустить два имени для одной ссылки. В ADR это фиксируется одной строкой.

Добавляется в `own_warehouses`:

```
code TEXT    -- короткий код филиала: MSK, KRD. Нужен для номеров документов (§8.3)
```

Ведение — только admin (Q8). `own_warehouses` уже в `DICTIONARY_TABLES`, стандартный CRUD
справочника переиспользуется как есть.

### 3.2 Слияние двух московских записей

Отдельным шагом миграции, до всего остального:

1. Выбрать выжившую запись, назвать «Москва», проставить `code = 'MSK'`.
2. Перенести на неё `warehouse_rent_rates` второй записи; при совпадении `effective_from`
   ставки суммируются (аренда и так ведётся одной суммой — Q1).
3. Переставить на неё `material_expenses` с `source_kind='warehouse'` и `source_id` второй записи.
4. Вторую запись — в `is_deleted = 1`.

Шаг обратимый только вручную, поэтому идёт отдельной ревизией с проверкой сумм аренды
до и после.

### 3.3 Что получает `branch_id`

Колонка проставляется при создании и дальше **не меняется** — иначе разъедется уже
посчитанная аналитика прошлых периодов.

**Физический контур** (делать первым — он якорь для всего остального):

| Таблица | Комментарий |
|---|---|
| `unloading_zones` | Зоны **и** ячейки адресного хранения — это одна таблица (различаются по `kind`). Филиал зоны = филиал всего, что в ней лежит |
| `zone_relocations` | Журнал остатков. Без этого поля остатки двух городов складываются в одну цифру |

**Документы:** `receipt_docs`, `shipment_docs`, `dispatch_docs`, `trip_docs`.
Строки (`*_lines`), журналы (`*_ops`) и файлы филиал не дублируют — берут через `doc_id`.
Исключение — `zone_relocations`: это самостоятельный журнал, читается напрямую.

**Люди:** `employees` (сотрудник филиала → его ЗП падает в расход филиала), `users` (§4).
Ставки, оклады, табель и выплаты — через `employee_id`.

**Деньги:** `material_expenses` (**NOT NULL**, Q6), `recurring_expenses`,
`extra_income_entries`, `storage_charges`, `invoice_docs`.

**Тарифы** (Q3): `product_packing_prices`, `client_pallet_prices`, `client_box_prices`,
`client_storage_prices` — см. §5.

### 3.4 Что филиал не получает — сознательно

Общие на компанию (Q4): `products`, `product_variants`, `product_barcodes`, `clients`,
`colors`, `sizes`, `product_types`, `suppliers`, `carriers`, `vehicle_types`, `positions`,
`expense_categories`, `expense_payment_sources`, `production_calendar`.

Один товар одного клиента может лежать в обоих городах; расщепление номенклатуры сломало бы
связку с маркетплейсами и ЛК клиента и удвоило ведение справочников.

Отдельно: **тариф логистики клиента таблицей не является.** В P&L доход логистики берётся
из `receipt_docs.logistics_cost` / `dispatch_docs.logistics_cost` — ручного поля документа.
Документ уже принадлежит филиалу, поэтому логистика делится сама, без правок в §5.

## 4. Доступ: филиал + три галочки

### 4.1 Поля пользователя

```
users.branch_id          TEXT     -- домашний филиал (обязателен для складских ролей)
users.branch_access      TEXT     -- 'own' | 'all', default 'own'
users.perm_view_costs    INTEGER  -- NULL = по роли, 0/1 = явное переопределение
users.perm_view_pnl      INTEGER  -- NULL = по роли
users.perm_view_invoices INTEGER  -- NULL = по роли
```

`NULL` означает «как решает роль» — существующее поведение сохраняется для всех, пока
галочку не поставили. Значение `0/1` перекрывает роль в обе стороны: можно и открыть
начальнику склада P&L его филиала, и закрыть менеджеру счета.

Домашний филиал есть у всех, включая пользователей с областью `all` — он подставляется
по умолчанию при создании расхода и документа (прямое требование из Q6: «у менеджера
Москвы по умолчанию Москва, у другого — его город»).

### 4.2 Почему это дёшево

Все три права уже централизованы в `backend/security.py`: `can_view_costs`,
`can_manage_finance`/`ensure_finance_access`. Роутеры `invoices`, `pnl` и `expenses`
зовут гейт по одному разу каждый, в зависимости на входе. Правка — внутри трёх функций:

```python
def can_view_costs(user) -> bool:
    override = user["perm_view_costs"]
    if override is not None:
        return bool(override)
    return user["role"] in ("admin", "manager")
```

Полную систему прав с чекбоксами по разделам (Q7) **не делаем**: она переписывает всю
ролевую матрицу и стоит 10–15 дней. Если понадобится — это отдельный проект после
филиалов; три флага мигрируются в него как пресет.

### 4.3 Область видимости

- `branch_access='own'` — только свой филиал. Кладовщик, начальник смены, начальник склада.
- `branch_access='all'` — все филиалы, сводные цифры и разрез «по филиалам».
- `role='admin'` — всегда `all`.
- `role='client'` — ось филиала не применяется, изоляция по `client_id` (§7.3).

Таблицу «пользователь ↔ несколько филиалов» (M:N) не заводим: случай «видит 2 из 3»
пока не существует, а `CLAUDE.md` §4 требует дождаться второго реального повторения.
Апгрейд до M:N возможен без потери данных.

### 4.4 Проброс в сессию

`modules/auth/service.py`: три места читают пользователя из БД
(`get_user_by_email`, `_get_user_by_refresh_cookie`, `get_current_user`) — во все три
добавить новые поля в `SELECT`. JWT **не** расширять: и область видимости, и галочки
должны отзываться мгновенно, а не по истечении access-токена.

`/me` начинает отдавать `branch_id`, `branch_access`, три флага и список доступных филиалов.

## 5. Филиальные тарифы (Q3)

Четыре effective-dated таблицы получают `branch_id` в ключ поиска:

| Таблица | Текущий ключ | Новый ключ |
|---|---|---|
| `product_packing_prices` | `(product_id, client_id, quality, effective_from)` | `+ branch_id` |
| `client_pallet_prices` | `(client_id, effective_from)` | `+ branch_id` |
| `client_box_prices` | `(client_id, effective_from)` | `+ branch_id` |
| `client_storage_prices` | `(client_id, effective_from)` | `+ branch_id` |

Фолбэка на общую цену нет (решение Q3): нет цены филиала на дату — услуга не тарифицируется.

**Практическое следствие, которое надо закрыть инструментами.** Цена упаковки заводится
не одной строкой на клиента, а на связку **товар × клиент × качество**. У активного
клиента это десятки и сотни строк. Требовать завести их для Краснодара вручную —
нереалистично, и без инструментов запуск филиала встанет именно здесь. Поэтому в объём
входят два инструмента, без которых решение Q3 не работает:

1. **Копирование тарифов между филиалами** — «скопировать все действующие цены филиала А
   в филиал Б на дату X», с предпросмотром количества строк. Дальше правятся только те,
   что отличаются.
2. **Отчёт «Пробелы в тарифах филиала»** — что тарифицировалось бы нулём: связки
   товар × клиент × качество без цены, клиенты без цены палеты / короба / хранения.
   Смотрится перед запуском филиала и после заведения нового товара.

Плюс защита при выставлении счёта: услуга без цены филиала попадает в счёт **видимым
пробелом**, а не строкой на ноль рублей.

Миграция: все действующие тарифы перезаводятся на Москву. Краснодар стартует пустым —
это ожидаемо и закрывается инструментом копирования.

## 6. Аналитика: правила атрибуции

От этого зависит, сойдётся ли P&L филиала. Источники дохода и расхода в
`modules/pnl/service.py` и `modules/expenses/service.py` атрибутируются по разным событиям,
поэтому филиал у каждого берётся из своего места:

| Источник | День (как сейчас) | Филиал берётся из |
|---|---|---|
| Доход: упаковка (годное/брак) | `zone_relocations.packed_date` | `zone_relocations.branch_id` |
| Доход: логистика клиента | `trip_docs.arrived_at` | `trip_docs.branch_id` |
| Доход: палеты | тот же рейс | `trip_docs.branch_id` |
| Доход: короба | тот же рейс | `trip_docs.branch_id` |
| Доход: доп. работы | `entry_date` | `extra_income_entries.branch_id` |
| Доход: хранение | `charge_date` | `storage_charges.branch_id` |
| Расход: ЗП | табель, по дням | `employees.branch_id` |
| Расход: аренда | размазка по рабочим дням | `own_warehouses` — филиал и есть склад |
| Расход: логистика рейса | `spent_on` | `trip_docs.branch_id` через `source_kind='trip'` |
| Расход: хозрасходы и накладные | `spent_on` | `material_expenses.branch_id` (NOT NULL) |
| Расход: скидки в счёте | `invoice_discounts` | `invoice_docs.branch_id` |

Эндпоинты, которым нужен параметр `branch_id` и разрез:

- `/pnl`, `/pnl/monthly`, `/pnl/income`, `/pnl/day`, `/pnl/trips`, `/pnl/logistics`
- `/expenses`, `/expenses/summary`, `/expenses/analytics`
- `/balances`, `/balances/grouped`, `/balances/summary`, `/balances/zones`,
  `/balances/plannable`, `/balances/turnover`, `/balances/turnover/history`, `/balances/relocations`
- `/dashboard/today`, `/dashboard/operational-plan`
- `/invoices`, `/extra-income`, отчёт «Хранение»
- `/timesheet/*` (неделя, выплаты, производительность упаковки)
- списки `/receipts`, `/shipments`, `/dispatches`, `/trips` и их summary-эндпоинты

Разрез «по филиалам» — это `GROUP BY branch_id` в тех же сервисах, где уже есть
`GROUP BY client_id`. Отдельного «аналитического» модуля не заводим.

## 7. Механизм изоляции

Мест, где читаются документные таблицы, — около 279. Править их поштучно вслепую —
гарантированная утечка. Нужен один узкий контракт.

Новый модуль `backend/branch_scope.py` — рядом с `security.py` и той же природы: сквозной
хелпер авторизации, а не «универсальная абстракция».

| Функция | Где применяется | Поведение |
|---|---|---|
| `visible_branch_ids(user)` | база для остальных | `None` = все филиалы; иначе список |
| `resolve_branch_filter(user, requested)` | каждый list / аналитический эндпоинт | запрошенный филиал ∩ область пользователя; чужой → 403 |
| `ensure_branch_access(user, branch_id)` | каждый detail / write | сразу после загрузки документа, до проверки статуса; чужой → **404** |
| `branch_sql(alias, branches)` | сервисные запросы | пустой фрагмент для `all`, `AND alias.branch_id IN (…)` иначе |
| `default_branch_for_write(user, requested)` | создание документа и расхода | подставляет домашний филиал автора (Q6) |

404 вместо 403 на чужом документе — намеренно: факт существования документа чужого филиала
сам по себе информация.

**Fail-closed обеспечивается тестом, а не дисциплиной.** Изоляционный прогон обходит
зарегистрированные роуты приложения (`app.routes`), а не ручной список — иначе новый
эндпоинт молча выпадет из проверки. Забыл фильтр → красный CI, а CI блокирует деплой
([ADR 0001](adr/0001-ci-only-deployment-via-github-actions.md)).

## 8. Сквозные сценарии

### 8.1 Что ломается тише всего

| Место | Сейчас | Если не тронуть |
|---|---|---|
| `modules/tasks` | «Мои задачи» фильтруются только по роли | Кладовщик Краснодара увидит в очереди московскую разгрузку |
| `modules/push` | Рассылка тоже по роли | Ночные пуши «Новая задача» летят не тому городу — самый заметный людям баг |
| `modules/scan` | Контекст по ШК/QR ищется глобально | Скан в Краснодаре откроет московский документ |
| `storage_charges` | Уникальный индекс `(client_id, charge_date)` | **Второй филиал физически не сможет начислить хранение тому же клиенту в тот же день** |
| `unloading_zones` | Флаги «зона упаковки» / «зона отгрузки» — **глобальные синглтоны** | **Заведение второго филиала ломает первый.** Разбор ниже |
| `unloading_zones.name` | Глобальный `UNIQUE` на имени места, код ячейки без филиала | **Краснодар не заведёт свою адресную сетку.** Разбор ниже |
| `trip_lines` | Привязка документа к рейсу не сверяет филиал | Московское поступление принимается краснодарским рейсом — журнал и документ расходятся навсегда (§8.7) |
| `find_duplicate_*` | Ключ дубля «клиент × груз × дата × состав» без филиала | Второй филиал получает ложное «такой документ уже есть» с номером и автором чужого (§8.7) |
| `_alerts_cache` | Процессный кеш счётчика счетов без ключа | Бейдж «к оплате / просрочено» до 20 с показывает цифры чужого филиала (§8.8) |
| `PUSH_STORM_THRESHOLD` | Порог шторма пушей на всю компанию | Утренний пик двух городов глушит пуши **обоим** — и помечает задачи отправленными (§8.2) |

#### Зона упаковки и зона отгрузки — глобальные синглтоны

Отдельно, потому что это **блокер создания второго филиала**, а не просто задача.

`set_packing_zone` в `modules/dictionaries/service.py` снимает флаг со всех остальных зон
одним запросом:

```sql
UPDATE unloading_zones SET is_packing_zone = CASE WHEN id = ? THEN 1 ELSE 0 END
```

То есть зона упаковки в системе ровно одна на всю компанию. Назначив зону упаковки
Краснодару, вы **снимете её с Москвы** — и Москва перестанет упаковывать. То же со
«Зоной отгрузки».

Хуже того, потребитель флага в `modules/balances/service.py` резолвит зону так:

```sql
SELECT ... FROM unloading_zones WHERE is_packing_zone = 1 AND COALESCE(is_deleted,0) = 0
ORDER BY created_at LIMIT 1
```

Без филиала. Даже если сделать флаги пофилиальными, но не тронуть этот запрос,
упакованный в Краснодаре товар поедет в **московскую** зону.

Это второй случай после авто-промоута отгрузок (§8.2), где пропуск филиала не показывает
лишнее, а делает неверное действие с товаром. Флаги становятся уникальными **в пределах
филиала**, резолв зоны принимает филиал обязательным параметром. Этап 2, в приёмку входит
явно: у каждого филиала своя зона упаковки и своя зона отгрузки, назначение одной не
трогает другую.

#### Код ячейки глобально уникален — второй блокер заведения филиала

Тот же справочник, другая поломка, и она тоже не даёт запустить Краснодар.

Зоны и ячейки лежат в одной таблице, а `unloading_zones.name` с baseline несёт
глобальный `UNIQUE`. Код ячейки собирается из координат без филиала:

```
format_cell_code(room, rack, section, floor) -> «1-А-10-1»
```

У краснодарского склада будет помещение «1», стеллаж «А», секция «01», этаж «1» —
ровно те же координаты, что в Москве. Дальше:

- `create_location` отдаёт `400 «Ячейка "1-А-10-1" уже существует»`;
- `bulk_create_locations` **молча** считает совпадения пропущенными: он заранее
  вычитывает существующие имена и увеличивает `skipped`, не поднимая ошибку.
  Мастер вернёт «создано 0, пропущено 240», и это прочтётся как «уже заведено».

Опаснее отказа то, что происходит потом: кладовщик Краснодара видит в справочнике
мест «1-А-10-1» — московскую запись, филиала в интерфейсе нет — кладёт туда товар,
и `zone_relocations` пишет краснодарский приход в московскую ячейку.

Решение того же вида, что у флагов: имя места уникально **в пределах филиала**
(частичный уникальный индекс `(branch_id, name)`), список и резолв мест принимают
филиал. Этап 2, в приёмку входит явно: два филиала заводят одинаковую адресную
сетку и не видят ячеек друг друга.

Это же исправляет ошибку в §9.5 B: строка «Ячейки — массовое создание уже умеет»
верна только для одного филиала.

### 8.2 Фоновые циклы: работают без пользователя, `branch_scope` к ним неприменим

В `app.py` живут четыре фоновых цикла. У них нет `user`, поэтому область видимости их
не защищает — филиал они обязаны учитывать **явно**. Два из четырёх без правки дают не
проблему видимости, а неверные данные.

| Цикл | Что делает | Что сломается без филиала |
|---|---|---|
| `_dispatch_autopromote_loop` | `autopromote_ready_dispatches`: раз в минуту двигает отгрузки «Ожидание упаковки» → «Подготовка», как только спрос покрыт готовым остатком | **Порча документов.** Отбор идёт по всем отгрузкам, а `preparation_gate_blocked` смотрит готовый остаток глобально: краснодарская отгрузка молча переедет в «Подготовку» на московском остатке. Ни ошибки, ни следа — только неверный статус |
| `_accrual_loop` → `run_storage_accruals` | Начисление хранения по клиентам с тарифом | Дедуп читает `storage_charges WHERE client_id = ?` без филиала: первый начисленный филиал закроет день для второго. Разворачивается в цикл по (клиент × филиал), тариф берётся филиальный |
| `_accrual_loop` → ЗП / аренда / регулярные | Пишет строки в `material_expenses` | Поле филиала NOT NULL (Q6) — начисление упадёт, пока источник не начнёт его проставлять: ЗП от `employees.branch_id`, аренда от самого склада, регулярные от шаблона |
| `_push_notify_loop` | `notify_new_tasks`: диффит активную очередь задач против `push_notified_tasks` | Пуш «Новая задача» уходит не тому городу (§8.1). Плюс порог шторма — см. ниже |
| `_mp_sync_loop` | Опрос FBS-заказов | Сейчас read-only, документов не создаёт — не блокер; см. §8.3 |

`autopromote` — единственное место в плане, где пропуск филиала портит данные, а не
только показывает лишнее. Держать внутри этапа 3 и покрыть отдельным тестом:
краснодарская отгрузка **не** промоутится, когда готовый остаток есть только в Москве.

**Порог шторма пушей тоже глобальный.** `notify_new_tasks` считает дифф по всей
компании (очередь берётся за `role='admin'`), после чего:

```python
storm = len(new_items) > PUSH_STORM_THRESHOLD   # 20 по умолчанию
```

При шторме аудитория обнуляется для **всех** новых карточек, но в
`push_notified_tasks` они записываются — то есть пуши не откладываются, а теряются
навсегда. Сегодня 20 новых задач за минуту — аномалия; с двумя городами утренний пик
складывается в один тик, порог начинает пробиваться на штатной нагрузке и глушит
очередь обоих филиалов сразу. Симптом — «пуши иногда не приходят», причину будут
искать долго. Когда цикл станет пофилиальным, порог обязан считаться внутри филиала,
а не поверх объединённого диффа.

### 8.3 Резервирование остатка и маркетплейсы

**Резерв.** Готовый остаток удерживается за отгрузками в статусах подготовки
(`reserved_by_variant` в `modules/balances/service.py`, гейт `check_lines_have_ready`).
Пул резерва общий по варианту — с филиалами он считается в границах филиала, иначе
московская отгрузка будет резервировать краснодарский товар. Это часть этапа 2
(остатки), а не отдельная задача, но в приёмку этапа входит явно.

Формулировку приёмки этапа 2 надо брать шире, чем «резерв»: тем же вариантным пулом без
филиала пользуются ещё три места, и они не резервируют, а **пишут в журнал**, то есть
портят данные, а не показывают лишнее:

- `ready_zones_for_variant` — выбор ячеек-источников при выезде рейса
  (`consume_stock_for_dispatch`): FIFO-списание уедет в московские ячейки;
- `get_available_total` — гейт плана задачи упаковки (`_check_lines_covered_by_stock`);
- `_packed_lines_for_variant` — атрибуция отгруженного к строкам чужой задачи упаковки,
  а по строкам упаковки тарифицируется счёт, то есть это уже деньги.

Критерий приёмки: **остаток по варианту нигде не считается вне филиала** — с
перечислением этих вызовов. С формулировкой «отгрузка не резервирует чужой товар» они
проезжают мимо приёмки.

**Маркетплейсы.** Модуль в фазе 1 read-only: заказы FBS не порождают ни отгрузок, ни
упаковок, поэтому филиал им сейчас не нужен и в объём он не входит. Два следствия
записать сейчас, чтобы не всплыли неожиданно:

- список `/marketplaces/orders` и связки товаров видны всему менеджерскому составу —
  после разделения это единственный экран, где Краснодар увидит московские данные;
  либо закрыть его областью видимости в этапе 3, либо осознанно оставить общим;
- при переходе к фазе 2 (заказ порождает документ) придётся ответить, **какой филиал
  исполняет заказ**: по кабинету продавца (`mp_accounts`), по магазину клиента
  (`client_stores`) или выбором оператора. Это вопрос на будущее, не на сейчас.

### 8.4 Межфилиальное перемещение товара (Q5 — позже)

Перемещение Москва → Краснодар — это два события: списание в филиале А и приход в Б.
Когда дойдут руки, делать **не** через `from_branch_id/to_branch_id` в журнале, а парой
записей с разными `branch_id` и общим `transfer_id` — по образцу того, как отгрузка уже
списывает остаток журнальной записью, а не вычитанием строк.

Сам документ «Межфилиальная передача» — вне объёма. Но `branch_id` в журнале закладывается
сейчас, иначе потом придётся перекладывать историю.

### 8.5 Нумерация документов

Генераторы берут `MAX` по всей таблице: `WH-00001`, `SHP-0001`, `DSP-0001`, `TR-00001`,
`INV-0001`, `EXP-0001`. Со вторым филиалом номера начнут чередоваться между городами.

Решение: последовательность на филиал с кодом — `WH-KRD-00001`. Три обстоятельства
делают это дешёвым:

- генератор уже фильтрует хвост номера регулярным выражением `^[0-9]+$`, поэтому
  `WH-KRD-00001` **автоматически не попадает** в `MAX` московской последовательности —
  два формата сосуществуют без конфликта;
- глобальный `UNIQUE` на `doc_number` сохраняется как есть;
- московские номера **не переименовываем** — они уже в счетах и переписке. Москва остаётся
  на `WH-00001`, новые филиалы получают код.

Единственная правка по существу: advisory-lock в `next_invoice_number` /
`next_expense_number` ключуется на филиал (`hashtext('invoice_doc_number:' || branch_id)`),
иначе филиалы будут сериализоваться друг об друга без необходимости.

### 8.6 Счета (Q2)

`invoice_docs.branch_id NOT NULL`. Подбор документов в счёт (`invoice_receipts`,
`invoice_shipments`, `invoice_storage_charges`, `invoice_extra_income`) фильтруется по
филиалу счёта. Клиент, обслуживаемый обоими филиалами, получает два счёта — тарификация
и P&L при этом сходятся без логики распределения, что особенно важно теперь, когда тарифы
у филиалов разные (Q3).

### 8.7 Перекрёстные ссылки: филиал контейнера ≠ филиал вложенного документа

§8.6 закрывает этот вопрос для счёта — и только для счёта. Тот же вопрос стоит везде,
где один документ ссылается на другой, и в одном месте он опаснее счёта.

**Рейс.** `link_receipts` и `link_dispatches` в `modules/logistics/service.py` проверяют
существование документа, клиента, остаток к распределению и — у отгрузок — совместимость
типа груза (`_cargo_family`). Филиал не проверяется. По миграции 0102 у роли `manager`
область `all`, значит пикер легально покажет обе области, и ничто не помешает подцепить
московское поступление к краснодарскому рейсу.

Что происходит с товаром дальше:

- `receive_receipts_for_trip` проводит приёмку и раскладывает принятое по ячейкам
  разгрузки — московское поступление материализуется остатком в краснодарских ячейках;
- `cascade_dispatches_to_shipped` → `consume_stock_for_dispatch` списывает под чужой рейс
  и двигает статус в «Отгружено».

`branch_id` по инварианту I1 не меняется, поэтому документ навсегда остаётся в одном
филиале, а его журнальные движения — в другом. Остатки и P&L двух филиалов расходятся,
и починить это можно только руками. Это третий случай после авто-промоута (§8.2) и зон
(§8.1), где пропуск филиала портит данные, а не показывает лишнее.

**Изоляционный тест это не поймает по устройству.** §11.1 обходит роуты и проверяет, что
в **ответах** нет чужих id; здесь чужой id приходит в **теле POST**. Нужен отдельный
инвариант и отдельный тест: филиал ссылаемого документа обязан совпадать с филиалом
контейнера, иначе 400. Проверять там же, где уже стоит гейт совместимости груза.

**Проверка дублей.** `find_duplicate_receipts` / `find_duplicate_shipments` /
`find_duplicate_dispatches` ключуются как «клиент × тип груза × дата × точный состав
строк». Клиент, обслуживаемый обоими филиалами, регулярно даёт одинаковый состав в один
день в двух городах — это норма, а не ошибка. Краснодарский менеджер получит
предупреждение «такой документ уже есть, № WH-00123, автор Иванов» и, скорее всего, не
станет создавать свой. Портит данные косвенно, через решение оператора, плюс выдаёт номер
и автора чужого документа. Эндпоинты `POST /*/check-duplicate` тест §11.1 тоже не обходит.

Оба — этап 3.

### 8.8 Процессный кеш счётчика счетов

`modules/invoices/service.py` держит единственный in-process кеш в backend:

```python
_ALERTS_TTL_SEC = 20.0
_alerts_cache = {"at": 0.0, "value": None}   # ключа нет
```

Кешируется «общий срез» — тот самый, который после разделения станет «срез моего
филиала». Первый, кто дёрнул `/invoices/alerts` в двадцатисекундном окне, отдаёт свои
цифры всем остальным: краснодарский финансист получит бейдж «просрочено 4» с московскими
счетами, и наоборот.

Это показывает лишнее, а не портит данные. Важно другое: находка невидима для §11.1 —
на холодном кеше тест проходит, поломка воспроизводится только двумя запросами подряд.
Ключевать на `(область видимости, client_id)` либо не кешировать при включённом скоупе.
Этап 4, вместе с `/invoices`.

- Колонка/бейдж «Филиал» в списках; разрез «По филиалам» в P&L и расходах — там же, где

- Галочки доступа — на карточке пользователя в `ui/routes/admin.tsx`.
- Отчёт «Пробелы в тарифах филиала» и мастер копирования тарифов (§5).

### 9.2 Mobile

`mobile/src/api/` — параллельная копия. `parity.test.ts` сверяет только одноимённые
union-типы и `*_LABELS`, поэтому новые object-типы в слепой зоне — паритет проверять руками.
Раскладка табов по роли (`tabsForRole`) не меняется: фильтрация целиком на backend,
приложение просто получает меньше данных.

### 9.3 ЛК клиента

`/cabinet/*` изолирован по `client_id`, и филиал для клиента — **не ограничение, а разрез**:
это его товар, он обязан видеть его весь, в каком бы городе тот ни лежал.

#### Главное правило: измерение появляется только у того, кому оно нужно

Большинство клиентов обслуживается **одним** филиалом. Для них ЛК не меняется ни на пиксель:
ни колонки, ни фильтра, ни лишнего слова. Разрез включается только у клиента, у которого
есть активность больше чем в одном филиале.

Признак — на стороне backend: `/cabinet/profile` (и `/cabinet/summary`) отдают список
филиалов, где у клиента есть остаток или документы. Пришёл один — фронт не рисует
ничего связанного с филиалами. Пришло два — включается разрез на всех экранах.

ЛК это витрина продукта; загромождать её измерением, которого у большинства клиентов нет,
дороже, чем один флаг в ответе.

#### По экранам

| Экран | Что меняется у клиента с двумя филиалами |
|---|---|
| **Остатки** (`/cabinet/balances`) | Ключ строки становится «вариант × филиал»: одна позиция в двух городах — две строки с колонкой «Филиал». Складывать нельзя: клиент увидит 5000 шт. и попросит отгрузить их из Краснодара, где лежит 1000. Карточки-итоги вверху (хранение / упаковка / готово / брак) — с разбивкой по филиалам |
| **Экспорт остатков** (xlsx) | Колонка «Филиал» добавляется **только** при двух и более филиалах. Формат согласован с клиентом («Pack Men Остатки на дата»), клиенты грузят файл в свои таблицы — у однофилиального клиента файл обязан остаться прежним |
| **Поступления**, **Отгрузки** (списки) | Колонка и фильтр «Филиал» |
| **Карточки документов** | Строка «Филиал» в шапке — обязательна независимо от числа филиалов: номер документа теперь несёт код (`WH-KRD-00001`), клиент это увидит и спросит, что значит `KRD`. Ответ должен быть на той же странице |
| **Дашборд** (`/cabinet`) | Итоги остатка — с разбивкой; активные поступления и отгрузки — с бейджем филиала; лента событий — с бейджем. Иначе «принято 300 шт.» без указания города бесполезно |
| **Списания / брак** | Колонка «Филиал» |
| **Отчёт по упаковке** | **Разрез по филиалам обязателен** — см. ниже |
| **Товары**, карточка товара | Номенклатура общая (Q4) — не меняется. Остаток на карточке — с разбивкой по филиалам |
| **Профиль** | Список обслуживающих филиалов. Здесь клиенту нужен **адрес**, а у `own_warehouses` его нет — добавляется поле `address` (см. ниже) |

#### Отчёт по упаковке обязан биться со счётом

Связка, которую легко упустить: счёт теперь выставляется **на филиал** (решение Q2), и
клиент, обслуживаемый обоими, получает **два счёта**. Отчёт по упаковке в ЛК — то, чем
клиент эти счета сверяет. Если отчёт даёт одну цифру за период, а счетов два, сверить
их невозможно и первый же разговор будет про «почему у вас не сходится».

Поэтому `/cabinet/reports/packing` получает разрез по филиалам, и суммы в разрезе обязаны
совпадать с тарифицированным в соответствующем счёте. Это отдельный тест, а не «должно
сойтись само».

#### Адрес филиала

Если филиал показывается клиенту, у него должен быть человекочитаемый адрес — иначе
«Краснодар» не отвечает на вопрос «куда везти». В `own_warehouses` адреса нет; добавляется
`address TEXT` рядом с `code` (этап 1, та же миграция) и отдаётся в `/cabinet/profile`.

#### Ловушка: fail-closed + клиент без филиала = пустой ЛК

Учётной записи клиента филиал **не назначается** (§4.3), то есть `branch_id` у неё `NULL`.
Область видимости работает fail-closed. Значит, если кто-то по невнимательности применит
`branch_scope` к `/cabinet/*` — клиент увидит **пустой кабинет**, и это будет выглядеть как
«потеряли товар», а не как ошибка прав.

Защита: `branch_scope` к `/cabinet/*` не применяется никогда — это записано инвариантом
в ADR 0002 и проверяется отдельным кейсом в изоляционном тесте (клиент с остатком в двух
филиалах видит оба, а не ноль). Изоляционный тест §11.1 обходит все роуты и по умолчанию
ожидает пустоту у чужого филиала — маршруты `/cabinet/*` из этого правила исключаются явным
списком, иначе тест «докажет» ровно ту поломку, которую должен ловить.

### 9.4 Эксплуатация: как заводится филиал и переводятся люди

Отдельный раздел, потому что тут план был слабее всего: модель разделения продумана,
а работа администратора в день открытия Краснодара — нет.

**Как поля пользователя правятся сегодня.** `UsersFeature.tsx` сохраняет каждое поле
отдельным запросом со своим тостом: роль, отображаемое имя, клиент — три независимых
`PATCH`. Если тем же способом добавить филиал, область видимости и три галочки прав,
на одного человека выйдет **шесть отдельных сохранений**, и каждое из них отзывает его
сессии (см. инвариант I4 ADR 0002 — иначе доступ не отзовётся). Открытие филиала на
восьмерых превращается в полсотни сохранений и восемь человек, разлогиненных по пять раз.

Поэтому в объём входит:

1. **Один экран «Доступ» с одним сохранением.** Вместо `PATCH /users/{id}/branch`
   и `PATCH /users/{id}/permissions` — единый `PATCH /users/{id}/access`, принимающий
   филиал, область и три флага разом. Сессии отзываются один раз, тост один.
   Роль логично отправить туда же, но её правка уже живёт своим эндпоинтом и своим
   набором проверок — трогать не будем, это отдельная задача.
2. **Массовый перевод.** `POST /users/bulk-access` — выбрать несколько человек в списке
   и назначить им филиал и область разом. Открытие филиала это именно такая операция,
   и делать её по одному человеку незачем.
3. **Фильтр и колонка «Филиал» в списке пользователей** — иначе после разделения
   непонятно, кто где, а список плоский.

**Филиал живёт в двух местах.** Учётная запись (`users.branch_id`) и сотрудник табеля
(`employees.branch_id`) — разные сущности, между ними уже есть связь `employees.user_id`
(её ведёт админ в карточке сотрудника). Рассинхрон реален: человека перевели в Краснодар
как пользователя, а в табеле он остался московским — и его ЗП продолжит падать в расход
Москвы. Решение без новых сущностей: при смене филиала учётной записи, у которой есть
связанный сотрудник, показывать в подтверждении, что филиал сотрудника тоже изменится,
и менять оба. Обратная сторона (правка сотрудника) — только предупреждение.

**Пользователь без филиала.** Новый сотрудник регистрируется сам и получает роль `user`
без филиала. Сегодня это не проблема, после разделения он увидит пустые экраны без
объяснения. Область видимости обязана работать fail-closed (пусто), но интерфейс должен
говорить прямо: «Филиал не назначен — обратитесь к администратору». Проверяется на
`/me`, показывается вместо контента, а не поверх пустых таблиц.

**Мобилка должна показывать филиал.** Кладовщику не нужен селектор, но нужно видеть,
в каком он городе — в шапке рядом с именем. При одном складе это было неважно, при двух
это первое, что спросят при разборе «почему я не вижу задачу».

**Чек-лист запуска филиала.** Заведение Краснодара — не одна кнопка, а последовательность:
филиал в «Наших складах» с кодом → зоны и ячейки → тарифы (копированием из Москвы,
§5) → сотрудники табеля → учётные записи с филиалом и областью → проверка отчёта
«Пробелы в тарифах». Оформить как раздел в `docs/onboarding-instance.md` — там уже
живёт ранбук развёртывания, и это его естественное продолжение.

### 9.5 Запуск нового филиала: что заработает само, а что руками

Вопрос «заведу филиал — всё заработает автоматом?» имеет честный ответ: **нет, и не должно.**
Часть данных неоткуда взять — ставку аренды, живых сотрудников, адрес. Но разница между
«полчаса настройки» и «две недели» решается тем, что мы заложим сейчас.

#### A. Работает само, ничего делать не нужно

Как только запись филиала создана:

- новый филиал сразу отдельная строка в P&L и в разрезе «по филиалам»;
- нумерация документов идёт со своим кодом (`WH-KRD-00001`) — отдельная последовательность
  заводится сама, ничего настраивать не надо (§8.5);
- селектор филиала, фильтры и колонки во всех списках подхватывают его из справочника;
- изоляция работает с первого дня: сотрудник нового филиала не видит чужого, и это
  гарантировано изоляционным тестом, а не настройкой;
- в ЛК клиента разрез включится сам, как только у клиента появится активность во втором
  городе (§9.3);
- начисления ЗП, аренды и хранения подхватят филиал автоматически, как только заведены
  сотрудники, ставка и тариф.

#### B. Копируется мастером за минуты — это надо построить

Отдельная задача этапа 6: **«Мастер запуска филиала»**, один экран, который делает
копируемую часть:

| Шаг | Механика | Уже есть? |
|---|---|---|
| Тарифы | Копирование всех действующих цен из выбранного филиала на дату (§5) | Строится в этапе 5 |
| Ячейки | Массовое создание: помещение, список стеллажей, число секций и этажей | **Не в текущем виде.** `LocationBulkCreateRequest` упрётся в глобальный `UNIQUE` на имени места и молча пропустит совпадающие адреса (§8.1). Работает после расщепления имён в этапе 2 |
| Зоны | Набор зон по шаблону другого филиала + назначение зоны упаковки и отгрузки | Появляется в этапе 2 |
| Шаблоны регулярных расходов | Копирование активных шаблонов с новым филиалом | Новое, мелкое |

Без мастера то же самое делается руками и занимает день-два; с мастером — минуты.
Строить его надо **после** этапов 2 и 5, когда копировать уже есть что.

#### C. Руками — и это нормально

Это реальные бизнес-данные, автоматизировать нечего:

- название, код и адрес филиала — одна форма;
- ставка аренды нового склада — одна запись;
- сотрудники табеля — живые новые люди;
- учётные записи и доступы — массовым назначением (§9.4);
- те тарифы, что отличаются от скопированных — правятся точечно поверх копии.

#### D. Порядок и проверка

Чек-лист (в `docs/onboarding-instance.md`, §9.4):

1. Завести филиал: название, код, адрес.
2. Ставка аренды.
3. Мастер запуска: тарифы копированием → зоны → ячейки → шаблоны расходов.
4. Сотрудники табеля, затем учётные записи с филиалом и областью.
5. **Отчёт «Пробелы в тарифах филиала»** (§5) — единственная проверка готовности:
   пусто значит филиал может выставлять счета. Не пусто — филиал примет и отгрузит товар,
   но не затарифицирует его, и это выяснится в конце месяца.

Реалистичный срок после того, как все этапы сделаны: **полчаса-час в системе** плюс время
на заведение людей. Шаг 5 — не формальность: именно он отличает «филиал работает» от
«филиал работает, а деньги не считаются».

| Ревизия | Содержание |

| `0104_branch_prices.py` | `branch_id` в четыре тарифные таблицы; действующие тарифы → Москва (§5) |
| `0105_branch_not_null.py` | `SET NOT NULL` — отдельной ревизией, после того как код перестанет писать NULL |

Индексы — фильтр по филиалу встанет почти в каждый запрос, поэтому `branch_id` идёт
**первым** в составных:

- `idx_zone_relocations_position` → `branch_id` первым (самый горячий индекс остатков)
- `idx_receipt_docs_client` → `(branch_id, client_id)`
- `idx_dispatch_docs_client` / `idx_dispatch_docs_status` → с `branch_id` первым
- `idx_material_expenses_spent_on` → `(branch_id, spent_on)`
- `idx_packing_prices_lookup`, `idx_client_pallet_prices_lookup` и аналоги → `+ branch_id`
- `storage_charges`: уникальный `(client_id, charge_date)` → `(client_id, branch_id, charge_date)`
- `unloading_zones`: глобальный `UNIQUE (name)` → частичный уникальный `(branch_id, name)`
  по неудалённым (§8.1) — без этого второй филиал не заведёт адресную сетку

Схему на test/prod ведёт только alembic; `_ensure_runtime_schema()` в `app.py` — dev-only,
туда ничего не класть.

**Новый инстанс.** `backend/bootstrap_instance.py` сегодня создаёт только администратора.
С обязательным филиалом у расхода чистый инстанс не сможет завести первую же трату,
поэтому бутстрап должен создавать филиал по умолчанию (имя из параметра, код — из имени)
и привязывать к нему созданного админа. То же касается `seed_test_data.py` и
`clear_inventory_test_data.py` — иначе dev-сиды перестанут проходить. Ранбук
[docs/onboarding-instance.md](onboarding-instance.md) дополняется шагом «завести филиал»
и чек-листом запуска (§9.4).

## 11. Тесты

### 11.1 Изоляционный — главный

`backend/tests/test_branch_isolation.py`:

- фикстура: два филиала, в каждом — поступление, упаковка, отгрузка, рейс, остаток,
  сотрудник, расход, счёт, начисление хранения, тариф;
- пользователь Краснодара с `branch_access='own'` обходит **все** зарегистрированные
  list/аналитические роуты приложения (обход `app.routes`, а не ручной список);
- ассерт: ни один ответ не содержит ни одного московского id;
- зеркальный прогон за Москву;
- отдельно: пользователь с `all` видит обоих и корректный разрез по филиалам.

### 11.2 Остальное

- `test_pnl.py` / `test_expenses.py` — суммы по филиалам сходятся к общему итогу.
- `test_balances.py` — остаток одного товара одного клиента в двух филиалах не смешивается;
  оборот сходится с каждой стороны.
- `test_pricing.py` / `test_pallet_pricing.py` / `test_box_pricing.py` /
  `test_storage_pricing.py` — цена ищется только по своему филиалу; **отсутствие цены
  филиала не даёт молчаливого нуля**, а видно как пробел.
- `test_storage_pricing.py` — начисление хранения одному клиенту в двух филиалах за один день.
- `test_invoices.py` — в счёт филиала не попадают документы другого филиала.
- `test_cabinet.py` — клиент с остатком в двух филиалах видит **оба** (а не ноль и не один);
  отчёт по упаковке в разрезе филиала сходится с тарифицированным в счёте этого филиала;
  у клиента с одним филиалом ответы и выгрузка xlsx не изменились.
- `test_locations.py` / `test_dictionaries.py` — назначение зоны упаковки в одном филиале
  **не снимает** флаг в другом; резолв зоны упаковки и отгрузки возвращает зону своего филиала;
  два филиала заводят **одинаковую** адресную сетку (`1-А-01-1` в обоих) — массовое создание
  создаёт, а не пропускает, и каждый видит только свои ячейки (§8.1).
- `test_dispatch.py` — **краснодарская отгрузка не промоутится авто-циклом**, когда готовый
  остаток есть только в Москве (§8.2); московская отгрузка не резервирует краснодарский товар;
  выезд рейса списывает только из ячеек своего филиала (§8.3).
- `test_logistics.py` — привязка поступления/отгрузки чужого филиала к рейсу отклоняется
  с 400 (§8.7); проверка дублей не находит документ другого филиала.
- `test_invoices.py` — счётчик алёртов не отдаёт цифры чужого филиала при двух запросах
  подряд внутри TTL кеша (§8.8).
- `test_push.py` — порог шторма считается внутри филиала: пик в одном городе не глушит
  пуши другого (§8.2).
- `test_storage_pricing.py` — фоновое начисление идёт по (клиент × филиал): начисление
  в одном филиале не закрывает день для другого.
- `test_tasks_visibility.py`, `test_push.py` — очередь задач и адресация пушей по филиалу.
- `test_security_roles.py` — матрица роль × галочки × область; `own` не может создать
  документ в чужом филиале; галочка перекрывает роль в обе стороны.
- `test_warehouse_rent.py` — суммы аренды до и после слияния записей совпадают.
- `test_users.py` — единое сохранение доступа отзывает сессии один раз; массовый перевод
  не трогает пользователей вне выборки; смена филиала учётки двигает связанного сотрудника.
- Frontend/mobile: `npm test` + сборка; ручная сверка паритета новых типов.

ячейки, перекрёстные ссылки рейса, вариантный пул остатка). При загрузке 10–15 ч/нед (как в `business-launch-plan.md`) это
5–9 календарных месяцев; при полной занятости — 6–10 недель.

Краснодара: без своих тарифов филиал не выставит счёт. Этап 7 нельзя переносить «на потом» —
без него нет доказательства, что R2 выполнено.

## 13. Риски

| Риск | Вероятность | Последствие | Митигация |
|---|---|---|---|
| Пропущенный фильтр на одном из ~279 SQL-мест | Высокая | Утечка данных филиала — прямое нарушение R2 | Изоляционный тест с обходом `app.routes`; CI блокирует деплой |
