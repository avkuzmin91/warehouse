# План доработок: филиалы и раздельная аналитика

Дата: 30.08.2026
Статус: черновик к согласованию (до начала кода — решить открытые вопросы §12)

Задача бизнеса: открыть второй филиал (Краснодар) со своими сотрудниками, поступлениями,
приёмками, упаковками и отгрузками. Аналитика — раздельная: сотрудник Краснодара не видит
цифры Москвы и наоборот. При этом должны быть роли, которые видят всё и сводно.

---

## 0. Конфликты, которые надо зафиксировать до кода

**1. Это архитектурное изменение.** `CLAUDE.md` §AI Agent Workflow п.5 запрещает менять
архитектуру без явного запроса. Запрос есть, но масштаб надо назвать честно: появляется
новая сквозная ось данных, которая проходит через 12+ backend-модулей, ~279 SQL-мест по
документным таблицам, ~20 миграций-эквивалентов схемы и **оба** api-слоя (`frontend/src/api`
и `mobile/src/api`). Такое решение положено закрепить ADR — `docs/adr/0002-branch-scoped-data-and-analytics.md`,
по образцу [0001](adr/0001-ci-only-deployment-via-github-actions.md).

**2. Конфликт с моделью «instance-per-client».** `docs/business-launch-plan.md` фиксирует
модель поставки «отдельный инстанс каждому клиенту, НЕ мультитенантный SaaS». Технически
филиал можно было бы сделать вторым инстансом — и это было бы дёшево. **Не подходит:**
требование «менеджеры видят всё» означает сводную аналитику по двум филиалам, а между
двумя инстансами сводной аналитики не существует. Плюс общая номенклатура, общие клиенты
и потенциальные межфилиальные перемещения. Значит — одна БД, филиал как измерение внутри
инстанса.

Важное следствие для продажи: та же механика («сеть складов в одном инстансе») становится
продуктовой фичей для операторов с несколькими площадками. Проектировать надо сразу как
фичу продукта, а не как хардкод под два города.

## 1. Требования

| # | Требование | Проверяемый критерий |
|---|---|---|
| R1 | Операционное разделение | Документ, зона, ячейка, остаток, сотрудник, задача принадлежат ровно одному филиалу |
| R2 | Изоляция аналитики | Пользователь с областью «свой филиал» ни на одном эндпоинте не получает данные чужого филиала |
| R3 | Сводный доступ | Есть область «все филиалы»: сводные цифры + разрез «по филиалам» |
| R4 | Обратная совместимость | Существующие данные целиком уезжают в филиал «Москва» без ручной разметки |
| R5 | Fail-closed | Новый эндпоинт, забывший фильтр, по умолчанию не отдаёт ничего лишнего (или падает в тестах) |

## 2. Модель данных

### 2.1 Сущность филиала

Новая таблица `branches` — минимальная, по образцу справочника:

```
branches (
  id, name, code, city, is_active,
  created_at, creator_id, updated_at, updated_by_id,
  is_deleted, deleted_at, deleted_by_id
)
```

`code` — короткий буквенный код (`MSK`, `KRD`) для номеров документов (§7.4).

**Почему отдельная таблица, а не переиспользовать `own_warehouses`.** «Наши склады» —
это физические площадки, на которых висит аренда (`warehouse_rent_rates`). У филиала
таких площадок может быть несколько (основной склад + мезонин + арендованный ангар),
а аренда обеих должна падать в P&L одного филиала. Поэтому:
`branches 1 — N own_warehouses` через `own_warehouses.branch_id`.

Если бизнес подтверждает «филиал = ровно один склад навсегда» (вопрос Q1 в §12), можно
удешевить: не заводить `branches`, а добавить область видимости прямо на `own_warehouses`.
Экономия ~1 день, но потолок жёсткий — расширять потом будет дороже, чем сделать сразу.
**Рекомендация: заводить `branches`.**

Регистрация в `DICTIONARY_TABLES` (`backend/config.py`) — да, чтобы получить стандартный
CRUD справочника; ведение — только admin.

### 2.2 Что получает `branch_id`

Колонка `branch_id TEXT NOT NULL REFERENCES branches(id)`, проставляется при создании и
дальше **не меняется** (иначе разъезжается уже посчитанная аналитика прошлых периодов).

**Физический контур (делать первым — он якорь для всего остального):**

| Таблица | Комментарий |
|---|---|
| `unloading_zones` | Зоны **и** ячейки адресного хранения — это одна таблица (`kind`). Филиал зоны = филиал всего, что в ней лежит |
| `zone_relocations` | Журнал остатков. Без этого поля остатки двух городов складываются в одну цифру |
| `own_warehouses` | Площадки филиала (носитель аренды) |

**Документы:**

| Таблица | Источник филиала при создании |
|---|---|
| `receipt_docs` | филиал автора / выбранный в шапке |
| `shipment_docs` | филиал автора |
| `dispatch_docs` | филиал автора |
| `trip_docs` | филиал автора (рейс приходит на конкретный склад) |

Строки (`*_lines`), журналы (`*_ops`), файлы — филиал **не дублируют**, берут через `doc_id`.
Исключение — `zone_relocations`: это самостоятельный журнал остатков, читается напрямую,
поле нужно.

**Люди:**

| Таблица | Комментарий |
|---|---|
| `employees` | Сотрудник табеля принадлежит филиалу → его ЗП падает в расход филиала |
| `users` | См. §3 — здесь не только принадлежность, но и область видимости |

`timesheet_entries`, `employee_rates`, `employee_salaries`, `payroll_payments` — через `employee_id`.

**Деньги:**

| Таблица | Комментарий |
|---|---|
| `material_expenses` | `branch_id` **nullable**: NULL = общефирменный расход (§6) |
| `extra_income_entries` | обязательный — доп. работа делается конкретным складом |
| `storage_charges` | обязательный; уникальный индекс `(client_id, charge_date)` → `(client_id, branch_id, charge_date)` |
| `invoice_docs` | обязательный (см. Q2 в §12 — один счёт на филиал или общий) |

`recurring_expenses` — шаблон получает `branch_id` (nullable, как у расхода), порождённые
начисления наследуют.

### 2.3 Что филиал НЕ получает — сознательно

Общие для всей компании: `products`, `product_variants`, `product_barcodes`, `clients`,
`colors`, `sizes`, `product_types`, `suppliers`, `carriers`, `vehicle_types`, `positions`,
`expense_categories`, `expense_payment_sources`, `production_calendar`, `record_actuality`.

Причина: один товар одного клиента может лежать в обоих городах; расщепление номенклатуры
по филиалам сломает связку с маркетплейсами и ЛК клиента и удвоит ведение справочников.

Тарифы (`pricing`, `pallet_pricing`, `box_pricing`, `client_storage_prices`) — общие
на первом этапе. Если в Краснодаре другие цены (вопрос Q3) — это отдельная задача:
добавить `branch_id` в ключ effective-dated тарифа с фолбэком на общий. **Не тащить в этот
этап**: тарифы участвуют в счетах и P&L, ошибка тут стоит денег.

## 3. Модель доступа

### 3.1 Поля пользователя

```
users.branch_id      TEXT   -- домашний филиал (обязателен для складских ролей)
users.branch_access  TEXT   -- 'own' | 'all', default 'own'
```

- `branch_access = 'own'` — видит только `branch_id`. Кладовщик, начальник смены,
  начальник склада Краснодара.
- `branch_access = 'all'` — видит все филиалы + разрез «по филиалам». Управляющий менеджер,
  собственник.
- `role = 'admin'` — всегда `all`, независимо от поля.
- `role = 'client'` — ось филиала не применяется, изоляция идёт по `client_id` (§8.3).

**Почему не таблица `user_branches` (M:N) сразу.** Она нужна только для случая «видит 2 из 3
филиалов». Пока филиалов два, случая не существует — а `CLAUDE.md` §4 требует ждать второго
реального повторения перед абстракцией. Поле `branch_access` покрывает оба заявленных
сценария и апгрейдится до M:N без потери данных.

Расширение роли: ортогональность сохраняется — «что можно делать» остаётся за `role`
(`backend/security.py`), «где можно делать» — за новой осью. Новых ролей не заводим.

### 3.2 Проброс в сессию

`modules/auth/service.py`: три места читают пользователя из БД
(`get_user_by_email`, `_get_user_by_refresh_cookie`, `get_current_user`) — во все три
добавить `branch_id, branch_access` в `SELECT`. JWT **не** расширять: область видимости
должна отзываться мгновенно, а не по истечении access-токена.

`/me` начинает отдавать `branch_id`, `branch_access` и список доступных филиалов —
фронту это нужно для селектора.

## 4. Механизм изоляции (ключевая инженерная часть)

Мест, где читаются документные таблицы, — около 279. Править их поштучно вслепую —
гарантированная утечка. Нужен один узкий контракт.

Новый модуль `backend/branch_scope.py` (рядом с `security.py`, той же природы — сквозной
хелпер авторизации, не «универсальная абстракция»):

```python
def visible_branch_ids(user) -> list[str] | None:
    """None — все филиалы (branch_access='all'/admin); иначе список разрешённых."""

def resolve_branch_filter(user, requested: str | None) -> list[str] | None:
    """Запрошенный в query филиал ∩ область пользователя. Чужой филиал → 403."""

def ensure_branch_access(user, branch_id: str) -> None:
    """Гейт detail/write-эндпоинта. Чужой документ → 404 (не 403: факт существования
    документа чужого филиала — тоже информация)."""

def branch_sql(alias: str, branches: list[str] | None) -> tuple[str, list]:
    """('' , []) для all; ('AND d.branch_id IN (?,?)', ids) иначе."""

def default_branch_for_write(user, requested: str | None) -> str:
    """Филиал создаваемого документа. 'own' — только свой, 'all' — обязан указать явно."""
```

Правила применения:

1. **Каждый list/аналитический эндпоинт** принимает опциональный `branch_id` (для
   `all`-пользователя — выбор разреза; для `own` — либо свой, либо 403) и прогоняет его
   через `resolve_branch_filter`.
2. **Каждый detail/write** — `ensure_branch_access` сразу после загрузки документа, до
   любой проверки статуса.
3. **Fail-closed** обеспечивается не дисциплиной, а тестом §10.1: изоляционный прогон по
   всему списку зарегистрированных роутов. Забыл фильтр — красный CI, а CI блокирует деплой
   ([ADR 0001](adr/0001-ci-only-deployment-via-github-actions.md)).

Разрез «по филиалам» для `all`-пользователя — это `GROUP BY branch_id` в тех же сервисах,
где уже есть `GROUP BY client_id` (`modules/pnl/service.py`, `modules/expenses/service.py`).
Отдельного «аналитического» модуля не заводим.

## 5. Аналитика: правила атрибуции

Это содержательная часть — от неё зависит, сойдётся ли P&L филиала. Источники дохода и
расхода в `modules/pnl/service.py` и `modules/expenses/service.py` атрибутируются по разным
событиям, поэтому филиал у каждого берётся из своего места:

| Источник | День (сегодня) | Филиал берётся из |
|---|---|---|
| Доход: упаковка (годное/брак) | `zone_relocations.packed_date` | `zone_relocations.branch_id` |
| Доход: логистика клиента | `trip_docs.arrived_at` | `trip_docs.branch_id` |
| Доход: палеты | тот же рейс | `trip_docs.branch_id` |
| Доход: короба | тот же рейс | `trip_docs.branch_id` |
| Доход: доп. работы | `extra_income_entries.entry_date` | `extra_income_entries.branch_id` |
| Доход: хранение | `storage_charges.charge_date` | `storage_charges.branch_id` |
| Расход: ЗП | табель, по дням | `employees.branch_id` |
| Расход: аренда | размазка по рабочим дням | `own_warehouses.branch_id → branches` |
| Расход: логистика рейса | `material_expenses.spent_on` | `trip_docs.branch_id` (через `source_kind='trip'`) |
| Расход: хозрасходы | `material_expenses.spent_on` | `material_expenses.branch_id` |
| Расход: скидки в счёте | `invoice_discounts` | `invoice_docs.branch_id` |

Эндпоинты, которым нужен параметр `branch_id` и разрез:

- `/pnl`, `/pnl/monthly`, `/pnl/income`, `/pnl/day`, `/pnl/trips`, `/pnl/logistics`
- `/expenses/analytics`, `/expenses` (реестр), `/expenses/summary`
- `/balances`, `/balances/grouped`, `/balances/summary`, `/balances/zones`,
  `/balances/plannable`, `/balances/turnover`, `/balances/turnover/history`, `/balances/relocations`
- `/dashboard/today`, `/dashboard/operational-plan`
- `/invoices`, `/extra-income`, отчёт «Хранение»
- `/timesheet/*` (неделя, выплаты, производительность упаковки)
- списки `/receipts`, `/shipments`, `/dispatches`, `/trips` и их summary-эндпоинты

## 6. Общефирменные расходы — отдельное решение

Не всякий расход принадлежит филиалу: бухгалтер, реклама, сервер, разработка, зарплата
собственника. Если их молча положить в Москву, P&L Москвы будет систематически хуже
краснодарского, и сравнение филиалов станет враньём.

Механика: `material_expenses.branch_id = NULL` → тип «Общефирменный».

Два режима отображения (решение — Q6 в §12):

- **A (рекомендуется на старте).** В отчёте филиала общие расходы не участвуют; в сводном
  отчёте — отдельная строка «Общие». Честно и не требует спорных допущений.
  Итог: `Прибыль компании = Σ прибыль филиалов − Общие`.
- **B.** Аллокация на филиалы по базе — по выручке или по ФОТ. Даёт «полную себестоимость
  филиала», но любая база спорна и порождает обсуждения на каждом закрытии месяца.

Реализовать A. База под B закладывается тем же полем — переключатель добавляется позже
одним параметром отчёта, без миграции.

## 7. Сквозные сценарии, которые надо решить явно

### 7.1 Межфилиальное перемещение товара

Сегодня `zone_relocations` двигает остаток между бакетами «опер. статус × качество» внутри
одного пространства. Перемещение Москва → Краснодар — это два события:
списание в филиале А и приход в филиале Б.

Рекомендация: **не** делать поле `from_branch_id/to_branch_id` в журнале. Вместо этого —
пара журнальных записей с разными `branch_id`, связанных общим `transfer_id`, по образцу
того, как отгрузка уже списывает остаток журнальной записью, а не вычитанием строк.
Так каждый филиал видит своё движение, и обе стороны сходятся в обороте `/balances/turnover`.

Сам документ «Межфилиальная передача» — **вне этого этапа** (нужен свой статусный цикл и
привязка к рейсу). Но `branch_id` в журнале закладывается сразу, иначе потом придётся
перекладывать историю.

### 7.2 Клиент обслуживается двумя филиалами

Остаток клиента — сумма по филиалам, в ЛК показывается разрезом. Вопрос счёта — Q2:
счёт на филиал (тогда клиент получает два) либо общий счёт с разбивкой строк.
Рекомендация: **счёт на филиал** — тарификация, `invoice_receipts`/`invoice_shipments`
и P&L тогда сходятся без дополнительной логики распределения.

### 7.3 Задачи, пуши, сканирование

- `modules/tasks/service.py::list_my_tasks` фильтрует только по роли — добавить филиал,
  иначе кладовщик Краснодара увидит в «Моих задачах» московскую разгрузку.
- `modules/push` рассылает по роли — та же правка, иначе ночные пуши будут прилетать
  не тому городу. Это самый заметный для людей баг из всех, если пропустить.
- `modules/scan` отдаёт контекст по ШК/QR — искать только в своём филиале.

### 7.4 Нумерация документов

`utils.next_doc_number` и его копии в `logistics`/`invoices`/`expenses` берут
`MAX(SUBSTR(...))` по всей таблице: `WH-00001`, `SHP-0001`, `DSP-0001`, `TR-00001`,
`INV-0001`, `EXP-0001`. Со вторым филиалом номера начнут чередоваться между городами —
неудобно людям и мешает в разговоре с клиентом.

Рекомендация: последовательность на филиал с кодом в номере — `WH-KRD-00001`.
Три обстоятельства делают это дешёвым:

- генератор уже фильтрует хвост номера регулярным выражением `^[0-9]+$`, поэтому
  `WH-KRD-00001` **автоматически не попадает** в `MAX` московской последовательности —
  два формата сосуществуют без конфликта;
- глобальный `UNIQUE` на `doc_number` сохраняется как есть;
- существующие московские номера **не переименовываем** — они уже в счетах и переписке.
  Москва остаётся на `WH-00001`, новые филиалы получают код. Несимметрично, но безопаснее
  и дешевле массового переименования.

Единственная правка по существу: advisory-lock в `next_invoice_number` / `next_expense_number`
должен ключеваться на филиал (`hashtext('invoice_doc_number:' || branch_id)`), иначе два
филиала будут сериализоваться друг об друга без необходимости.

## 8. Клиенты (фронт, мобилка, ЛК)

### 8.1 Frontend

- `api/typesUser.ts` — `branch_id`, `branch_access` в `User`.
- Новый `api/branchesApi.ts` (типы + CRUD + labels), `useLookups()` отдаёт `branches`.
- Селектор филиала в `ui/shell/Topbar` — только для `branch_access='all'`; выбранное
  значение живёт в URL через `useFilterParam('branch', '')`, как остальные фильтры
  (`CLAUDE.md` §7 прямо запрещает другие источники состояния фильтров).
- Для `own`-пользователя селектора нет: филиал один, шум в интерфейсе не нужен.
- Колонка/бейдж «Филиал» в списках и разрез «По филиалам» в P&L и расходах — там же,
  где сейчас разрез «По клиентам».
- Экран ведения филиалов — в `ui/routes/admin.tsx`.

### 8.2 Mobile

`mobile/src/api/` — параллельная копия. `parity.test.ts` сверяет только одноимённые
union-типы и `*_LABELS`, поэтому новый `Branch` (object-тип) в слепой зоне — паритет
проверять руками. Раскладка табов по роли (`tabsForRole`) **не меняется**: фильтрация
данных целиком на backend, приложение просто получает меньше.

### 8.3 ЛК клиента

`/cabinet/*` изолирован по `client_id` и оси филиала не получает: клиент видит свой товар
целиком. Добавляется только **фильтр** «Филиал» и колонка в остатках — чтобы клиент понимал,
где физически лежит его товар. Ограничением это не становится.

## 9. Миграция данных

Три ревизии подряд — так безопаснее, чем одна большая:

1. **`0101_branches.py`** — таблица `branches`; сид филиала «Москва» с фиксированным id
   (константа `BRANCH_DEFAULT_ID` в `config.py`, по образцу `RECORD_ACTUALITY_YES_ID`);
   `users.branch_id`, `users.branch_access`; бэкфилл всех пользователей в Москву,
   `branch_access='all'` для `admin` и `manager`.
2. **`0102_branch_scope_columns.py`** — `branch_id` во все таблицы §2.2 как **nullable**;
   бэкфилл `= BRANCH_DEFAULT_ID`; новые индексы.
3. **`0103_branch_not_null.py`** — `SET NOT NULL` там, где поле обязательное
   (`material_expenses` и `recurring_expenses` остаются nullable). Отдельной ревизией —
   чтобы прогнать её после того, как код перестанет писать NULL.

Индексы (важно для производительности — фильтр по филиалу встанет почти в каждый запрос):

- `idx_receipt_docs_client` → `(branch_id, client_id)`
- `idx_dispatch_docs_client` / `idx_dispatch_docs_status` → с `branch_id` первым
- `idx_zone_relocations_position` → `branch_id` первым (это самый горячий индекс остатков)
- `idx_material_expenses_spent_on` → `(branch_id, spent_on)`
- `storage_charges`: уникальный `(client_id, charge_date)` → `(client_id, branch_id, charge_date)`
  — **иначе второй филиал не сможет начислить хранение тому же клиенту в тот же день**

Схему на test/prod ведёт только alembic; `_ensure_runtime_schema()` в `app.py` — dev-only,
туда ничего не класть.

## 10. Тесты

### 10.1 Изоляционный тест — главный

`backend/tests/test_branch_isolation.py`:

- фикстура: два филиала, в каждом — поступление, упаковка, отгрузка, рейс, остаток,
  сотрудник, расход, счёт, начисление хранения;
- пользователь Краснодара с `branch_access='own'` обходит **все** зарегистрированные
  list/аналитические роуты приложения (обход `app.routes`, а не ручной список — иначе
  новый эндпоинт молча выпадет из проверки);
- ассерт: ни один ответ не содержит ни одного московского id;
- зеркальный прогон за Москву;
- отдельно: пользователь с `all` видит обоих и корректный разрез по филиалам.

### 10.2 Остальное

- `test_pnl.py` / `test_expenses.py` — суммы по филиалам сходятся к общему итогу; общие
  расходы не попали ни в один филиал.
- `test_balances.py` — остаток одного товара одного клиента в двух филиалах не смешивается;
  оборот сходится с каждой стороны.
- `test_tasks_visibility.py`, `test_push.py` — очередь задач и адресация пушей по филиалу.
- `test_security_roles.py` — матрица роль × область; в частности, `own` не может создать
  документ в чужом филиале.
- `test_storage_pricing.py` — начисление хранения одному клиенту в двух филиалах за один день.
- Frontend/mobile: `npm test` + сборка; ручная сверка паритета `Branch`-типов.

## 11. Этапы и оценка

Оценка в человеко-днях, при условии что открытые вопросы §12 закрыты до старта.

| # | Этап | Содержание | Оценка | Критерий приёмки |
|---|---|---|---|---|
| 0 | Решения | ADR 0002, ответы на Q1–Q8 | 0.5–1 | ADR в `main` |
| 1 | Фундамент | `branches`, поля `users`, `branch_scope.py`, `/me`, миграции 0101 | 3–5 | Филиал заводится, пользователь привязывается, `/me` отдаёт область |
| 2 | Физический контур | `unloading_zones`, `zone_relocations`, `own_warehouses`; balances, locations, scan | 4–6 | Остатки, зоны, ячейки и сканирование разделены |
| 3 | Документы | receipts, shipments, dispatch, logistics; tasks, push, dashboard | 5–8 | Краснодар не видит московских документов и задач; пуши адресные |
| 4 | Деньги и аналитика | expenses, extra_income, storage_charges, invoices, employees/timesheet, pnl | 6–10 | P&L филиала сходится; общие расходы отдельной строкой |
| 5 | Интерфейсы | селектор филиала, разрез «по филиалам», админ-экран, mobile | 4–6 | `all`-пользователь переключает разрез; `own` его не видит |
| 6 | Изоляция и закрытие | тест §10.1, миграция 0103 NOT NULL, прогон | 2–3 | Изоляционный тест зелёный на всех роутах |

**Итого ~25–39 человеко-дней.** При загрузке 10–15 ч/нед (как в `business-launch-plan.md`)
это 4–6 календарных месяцев; при полной занятости — 5–8 недель.

Этапы 1–2 обязательны и неделимы. Этапы 3–5 можно поставлять по одному домену за раз:
после этапа 2 система работоспособна, просто ещё не всё разделено. Этап 6 нельзя переносить
«на потом» — без него нет гарантии, что R2 действительно выполнено.

## 12. Открытые вопросы к бизнесу

Ответы нужны **до** этапа 1 — каждый меняет схему.

| # | Вопрос | Что зависит |
|---|---|---|
| Q1 | Филиал = ровно один физический склад, или их может быть несколько? | Отдельная таблица `branches` vs. флаг на `own_warehouses` (§2.1) |
| Q2 | Клиент, обслуживаемый обоими филиалами, получает два счёта или один сводный? | Структура `invoice_docs`, тарификация, P&L (§7.2) |
| Q3 | Тарифы клиента (упаковка / логистика / палеты / короба / хранение) — общие или свои у Краснодара? | Ключ effective-dated тарифов; при «свои» — +3–5 дней (§2.3) |
| Q4 | Номенклатура и SKU — общие на компанию? | Подтверждение решения §2.3; при «раздельные» модель меняется принципиально |
| Q5 | Межфилиальные перемещения товара нужны сейчас или позже? | Документ передачи: сейчас +4–6 дней, позже — 0 (задел в журнале всё равно делается) (§7.1) |
| Q6 | Общефирменные расходы: отдельной строкой или распределять на филиалы? | Режим A или B (§6) |
| Q7 | Начальник склада Краснодара видит деньги своего филиала (P&L, счета) или только операционку? | Матрица роль × область в `security.py` |
| Q8 | Кто заводит филиалы и переводит сотрудников — только admin? | Гейт CRUD `branches` и правки `users.branch_id` |

## 13. Риски

| Риск | Вероятность | Последствие | Митигация |
|---|---|---|---|
| Пропущенный фильтр на одном из ~279 SQL-мест | Высокая | Утечка данных филиала — прямое нарушение R2 | Изоляционный тест с обходом `app.routes` (§10.1); CI блокирует деплой |
| Деградация запросов остатков | Средняя | Медленный `/balances` на живом складе | Индексы с `branch_id` первым (§9); замер до/после на dev-БД |
| Расхождение P&L после разделения | Средняя | Потеря доверия к цифрам в момент запуска филиала | Тест «Σ по филиалам + Общие = прежний итог» на исторических данных |
| Пуши и задачи не тому городу | Средняя | Заметный людям сбой в первый же день | §7.3 в этапе 3, не переносить |
| Рассинхрон `frontend/src/api` и `mobile/src/api` | Средняя | Мобилка ломается на проде | Ручная сверка `Branch` (слепая зона `parity.test.ts`), §8.2 |
| Расползание объёма на тарифы и межфилиальные передачи | Высокая | Этап не закрывается месяцами | Q3 и Q5 закрыть словом «позже» письменно, до старта |
