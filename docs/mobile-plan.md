# Мобильное приложение кладовщика — план внедрения

Архитектурный план мобильного приложения для склада. Цель v1 — дать **кладовщику** инструмент на телефоне, чтобы выполнять складские операции у стеллажа, не возвращаясь к компьютеру.

Документ согласован с [CLAUDE.md](../CLAUDE.md): жёсткие границы слоёв, переиспользование `api/`-слоя, минимально необходимые изменения, без слома существующей архитектуры.

---

## 1. Решение (TL;DR)

- **Не отдельный продукт, а отдельное приложение в том же репозитории**, переиспользующее API-слой и типы, но с собственным mobile-first UI.
- **Стек:** Capacitor + React 19 + TypeScript + Vite (тот же, что на вебе).
- **v1 — только кладовщик**, только Android-APK (личные телефоны). iOS — вторым шагом.
- **Online-first** + очередь повторной отправки операций (без полноценного офлайна).
- **Backend переиспользуется целиком**; доработки точечные (мобильный auth, штрихкоды, CORS, идемпотентность).

---

## 2. Зафиксированные вводные

| Вопрос | Решение | Следствие |
|---|---|---|
| Целевые устройства v1 | Личные телефоны Android/iOS; ТСД — позже | Capacitor (Android+iOS из одного кода). Сканер v1 — камера, за интерфейсом `ScanSource` для последующего подключения аппаратных ТСД |
| Офлайн | Online-first + очередь повторов | Без локальной БД и разрешения конфликтов. Нужен кэш справочников + очередь write-операций с `request_id` |
| Дистрибуция | Внутренний APK (вручную/ссылка) | v1 = Android-APK. iOS sideload невозможен → iOS через TestFlight на этапе 3 |

---

## 3. Выбор стека и обоснование

| Вариант | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| **PWA** | Дёшево, ноль обвязки | Хуже доступ к камере/аппаратному сканеру на дешёвых Android, слабее офлайн, «установка со звёздочкой» | Запасной минимальный вариант |
| **React Native / Flutter** | Полностью нативный UX | Отдельная кодовая база, дублирование типов и API-функций, отдельная компетенция | Избыточно для внутреннего инструмента |
| **Capacitor + React** ✅ | Переиспользование `src/api/*` и TS-типов 1:1; нативная камера/сканер/push; Android+iOS; установка как APK | Webview-производительность (некритично для форм/списков) | **Выбран** |

Ключевой аргумент: Capacitor оборачивает существующий React-код и даёт нативные возможности там, где они реально нужны кладовщику (сканер штрихкодов), при максимальном переиспользовании TypeScript-слоя данных.

---

## 4. Структура репозитория

Монорепо с общим пакетом API-клиента — без дублирования слоя данных:

```
warehouse/
  backend/                       # архитектура без изменений
  frontend/                      # текущий веб (desktop-first)
  packages/
    api-client/                  # ВЫНЕСТИ сюда frontend/src/api/* + общие TS-типы
  mobile/                        # НОВОЕ: Capacitor + React, mobile-first UI
    src/
      api/      -> @wms/api-client     # переиспользование
      screens/                         # экраны кладовщика (свои)
      scan/                            # ScanSource + реализации (камера, позже ТСД)
      queue/                           # очередь write-операций (online-first)
      auth/                            # мобильный токен-стор (Secure Storage)
    android/                           # Capacitor Android-проект
    ios/                               # Capacitor iOS-проект (этап 3)
```

**Принцип:** переиспользуем **слой данных и типы**, UI пишем заново. Desktop-компоненты (`Table`, `FiltersBar`, `RelocationPanel`, `MoveToPackingDrawer`) table-heavy и под мобилку не годятся. Вынос `api/` чист, потому что по CLAUDE.md он уже изолирован от React/JSX.

## 5. Объём v1 — операции кладовщика

Из разбора кода у кладовщика (`warehouse_manager` / `warehouse_head`) 5 реальных операций. Паттерн мобильного экрана: **задача → (скан) → количество → подтвердить**.

| # | Операция | Эндпоинт | Файл backend |
|---|---|---|---|
| 1 | Мои задачи (стартовый экран) | `GET /tasks` | `modules/tasks/router.py` |
| 2 | Приёмка / разгрузка рейса | `POST /trips/{id}/unload` | `modules/logistics/router.py` |
| 3 | Передача на упаковку / возврат | `POST /shipments/{id}/lines/{lid}/move-to-packing`, `/return-from-packing` | `modules/shipments/router.py` |
| 4 | Раскладка по местам (годный/брак) | `POST /shipments/{id}/finish-relocation`, `/finish-defect-relocation` | `modules/shipments/router.py` |
| 5 | Остатки / поиск товара по месту | `GET /balances` | `modules/balances/service.py` |

Главная ценность: задача приходит на телефон → у стеллажа кладовщик сканирует товар и место → вводит количество → подтверждает. Сейчас это выпадающие списки на десктопе.

## 6. Доработки backend (минимум)

Бэкенд переиспользуется практически целиком. Точечные изменения:

### 6.1 Мобильная аутентификация
Сейчас refresh-токен в `HttpOnly cookie wms_rt` (`modules/auth/`). В нативной обёртке (схема `capacitor://localhost`) cookie к домену API — cross-site, работает ненадёжно.

- Добавить **мобильный режим логина**: `/auth/login` возвращает refresh-токен в теле ответа под флагом клиента (например, заголовок `X-Client: mobile`).
- Приложение хранит refresh в **Capacitor Secure Storage / Android Keystore**, access-JWT (TTL 60 мин) — в памяти.
- Ротацию и replay-protection (`auth_sessions`, `auth_refresh_superseded`) переиспользуем как есть.
- **Запрет:** никаких токенов в `localStorage`/`SharedPreferences`.

### 6.2 Штрихкоды (этап 2)
Сканирования в системе нет (есть только SVG-иконка). Чтобы сканер было «куда приземлить»:
- Миграция Alembic `NNNN_add_product_barcode.py` — поле `barcode` у товара/варианта.
- Эндпоинт `GET /products/by-barcode/{code}` → product/variant.

### 6.3 Идемпотентность write-операций
Мобильная сеть рвётся; повтор не должен задваивать приёмку.
- Клиент шлёт `request_id` (UUID) на write-эндпоинты.
- Сервер хранит обработанные `request_id` и возвращает прежний результат на повтор.

### 6.4 CORS
Разрешить прод-origin мобильного клиента в `CORS_ALLOW_ORIGINS`.

> Все изменения — в рамках существующих слоёв (`router → service → schemas`), без слома архитектуры. Статусы/op_type — из `config.py`, не хардкодить.

## 7. Что переиспользуется / что заново

**Переиспользуется как есть:**
- Backend целиком — эндпоинты кладовщика, RBAC-роли (`warehouse_manager`, `warehouse_head`, `shift_supervisor`), ротация refresh с replay-protection.
- API-слой и TS-типы — через `packages/api-client`.
- Русские лейблы и `formatApiErrorDetail`.

**Пишется заново:**
- Весь UI — mobile-first, крупные тач-цели, одна колонка.
- Сканер (`ScanSource`), очередь операций, мобильный токен-стор.

---

## 8. Нюансы (часто упускаются)

- **Офлайн.** v1 — online-first с retry-очередью на отправку (кэш справочников + очередь write при обрыве). Полноценный офлайн дорог: операции уменьшают остатки и конкурентны → нужно разрешение конфликтов. Отложено.
- **Безопасность токенов** — только Secure Storage.
- **Идемпотентность** — `request_id` на write-операциях (см. 6.3).
- **iOS-дистрибуция** — APK только Android. Для iOS нужен TestFlight/Ad Hoc (Apple Developer $99/год). v1 = Android.
- **Сканер за абстракцией** — `ScanSource` (камера сейчас, аппаратный ТСД позже) без переписывания экранов.
- **Русский UI/ошибки** — переиспользуем существующие лейблы.

## 9. Дорожная карта

### Этап 0 — фундамент (≈1 спринт)
- Вынести `frontend/src/api/*` → `packages/api-client`.
- Поднять `mobile/` (Capacitor + React 19 + Vite), сборка Android-APK с экраном логина.
- Backend: мобильный режим auth (refresh в теле под флагом), CORS.

### Этап 1 — ядро кладовщика (≈2–3 спринта)
- Экран «Мои задачи» (`GET /tasks`).
- «Приёмка рейса» (`POST /trips/{id}/unload`) — ручной ввод.
- Очередь write-операций с `request_id`; идемпотентность на сервере.
- e2e на реальном Android-телефоне.

### Этап 2 — сканер + остальные операции
- Миграция `barcode` + `GET /products/by-barcode/{code}`.
- Камерный сканер за `ScanSource`, интеграция в приёмку.
- Передача на упаковку / раскладка годного и брака / поиск по остаткам.

### Этап 3 — расширение
- iOS через TestFlight.
- Поддержка аппаратных ТСД (вторая реализация `ScanSource`).
- Push-уведомления о новых задачах (Capacitor Push).

---

## 10. Проверки перед завершением этапов

- Backend: `cd backend && pytest` (затронутые модули — `auth`, при штрихкодах `products`).
- Миграции: `cd backend && alembic upgrade head` на dev-БД.
- Mobile: сборка APK + e2e на реальном устройстве (эмулятор не покрывает камеру/сканер).
- api-client: type-check / build в `frontend/` после выноса слоя.
