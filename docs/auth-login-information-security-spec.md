# Техническое задание: вход в систему (логин)  
## Фокус: информационная безопасность (бизнес-язык)

**Версия:** 1.0  
**Статус:** описывает текущую целевую реализацию в продукте (WMS) и ожидания эксплуатации.

---

## 1. Цель документа

Зафиксировать **зачем** устроен вход в систему так, как он есть сегодня, и **какие риски для бизнеса** он закрывает: кража учётных записей, массовый перебор паролей, утечки сессий, злоупотребление после компрометации одного устройства.

Документ предназначен для **владельцев продукта**, **ИБ**, **эксплуатации** и **аудита**; детали реализации по файлам — в технических приложениях (`backend/docs/auth-rate-limit.md`, `frontend/docs/auth-browser-checklist.md`).

---

## 2. Что считается «входом в систему»

**Вход** — действие пользователя по проверке **email и пароля**, в результате которого:

- пользователь получает возможность работать в приложении в рамках своей роли;
- система выдаёт **краткоживущий доступ** (токен в памяти браузера) и **долгоживущую привязку сессии** (защищённая cookie на стороне браузера), не храня пароль после проверки.

**Не вход:** восстановление пароля по ссылке (если появится отдельно), регистрация, смена пароля уже внутри сессии — в ТЗ не раскрываются, кроме пересечений с cookie сессии.

---

## 3. Ценность для бизнеса (что защищаем)

| Актив | Почему важно |
|--------|----------------|
| **Учётные записи пользователей** | Доступ к складу, клиентам, отчётам, администрированию. |
| **Сессия после входа** | Компрометация сессии = работа от имени пользователя без знания пароля. |
| **Репутация и соответствие** | Инциденты с массовым подбором паролей и утечками сессий бьют по доверию и договорам. |

---

## 4. Основные угрозы (простым языком)

1. **Перебор паролей** с одного адреса в интернете или по одному email (целенаправленная атака на учётку).
2. **Подмена «кто пришёл»** за обратным прокси: злоумышленник подсовывает поддельные заголовки, чтобы обойти блокировки по IP.
3. **Кража токена доступа** из памяти/скриптов на странице (XSS) или из логов.
4. **Кража или повторное использование старой сессии** (украденный refresh, «запись» старого токена после выдачи нового).
5. **Отказ или обман сервиса ограничений** (сбой Redis, перегрузка телом запроса).
6. **Неверная настройка среды** (HTTP без защиты cookie в продакшене, слишком широкий CORS).

Требования ниже — это **минимально ожидаемое поведение** системы при этих угрозах.

---

## 5. Функциональные и ИБ-требования

### 5.1 Пароль и проверка учётных данных

- Пароль **не хранится и не передаётся** в открытом виде после установки: в базе — только результат **устойчивого хеширования** (современный алгоритм семейства bcrypt).
- При неверной паре **одинаковый ответ** для «нет такого email» и «неверный пароль», чтобы усложнить **сбор списка** существующих адресов через форму входа.

**Критерий для бизнеса:** нельзя по ответу сервера однозначно понять, существует ли email в системе.

---

### 5.2 Двухуровневая модель доступа после входа

| Уровень | Назначение | Как снижает риск |
|--------|------------|------------------|
| **Краткоживущий токен доступа** | Доступ к API из приложения | Укороченное «окно», если токен перехватят; хранение в оперативной памяти вкладки, а не в долговечной cookie по умолчанию. |
| **Долгоживущая сессия (cookie)** | Тихое продление работы без повторного ввода пароля | Cookie **только для HTTP-запросов** (не читается обычным JavaScript), ограничена **путём** приложения (`/api`), политика **SameSite** снижает риск утечки при переходах с чужих сайтов; в продуктивной среде включается **только по HTTPS** (`Secure`). |

**Критерий для бизнеса:** даже при XSS на странице приложения **нельзя просто прочитать** cookie сессии из скрипта — она не доступна JS.

---

### 5.3 Ограничение частоты попыток входа

- Учитываются попытки **по IP** и **по нормализованному email** (регистр и пробелы не помогают обойти лимит).
- В централизованном режиме (Redis) **в ключах не хранится сам email** — только необратимый отпечаток (хеш), чтобы снизить риск **утечки персональных данных** из кэша и длину ключей.
- При недоступности Redis поведение настраивается: либо **мягкий** режим (вход возможен с резервным ограничением по IP), либо **жёсткий** (временный отказ, если так задано политикой среды).

**Критерий для бизнеса:** массовый перебор паролей **заметно дороже** для атакующего; при сбое инфраструктуры лимитов **есть осознанная политика**, а не «тихий» отказ без логов.

---

### 5.4 Кто «настоящий» клиент за прокси

- Если запрос идёт **не через доверенный обратный прокси**, заголовки вида «подставь другой IP» **игнорируются** при расчёте лимитов — иначе злоумышленник мог бы **обойти блокировку по IP**.
- Список доверенных прокси задаётся **конфигурацией среды** (IP, подсети, имя сервиса в Docker-сети).

**Критерий для бизнеса:** лимиты и журналы считают **реального клиента**, а не произвольную строку в заголовке.

---

### 5.5 Защита от злоупотребления телом запроса

- Размер тела запроса на вход **ограничен**; превышение трактуется как попытка злоупотребления и **не доходит** до проверки пароля.

**Критерий для бизнеса:** нельзя «положить» обработчик входа гигантским JSON без отдельного решения по лимитам на уровне шлюза.

---

### 5.6 Повторное использование старой сессии (replay)

- После обновления долгоживущей сессии старый секрет **не должен** бесследно работать как «второй ключ».
- Если система видит **повторное использование уже заменённого** refresh-токена, применяется политика: в течение короткого окна — мягкая реакция, после — **отзыв всех сессий пользователя** (компрометация считается вероятной).

**Критерий для бизнеса:** украденный старый «долгий ключ» не даёт **долгосрочного параллельного** доступа рядом с легитимным пользователем без реакции.

---

### 5.7 Выход из системы и отзыв доступа

- При выходе **краткоживущий токен** помечается как недействительный в рамках сервера (список отзыва с ограничением размера — защита от исчерпания памяти).
- Cookie долгой сессии **сбрасывается** на стороне ответа сервера.

**Критерий для бизнеса:** «Выйти» означает **прекращение доверия** к ранее выданным элементам сессии в пределах заявленной модели.

---

### 5.8 Наблюдаемость (логи и метрики)

- События, связанные с ограничением входа и сбоями Redis, пишутся **структурированно** (удобно для SIEM и разбора инцидентов).
- Счётчик перехода на **резервный режим** при сбое Redis позволяет видеть **деградацию** до жалоб пользователей.

**Критерий для бизнеса:** при инциденте можно ответить на вопросы **когда**, **что за тип события**, **был ли реальный отказ входа**, без ручного разбора неструктурированных логов.

---

### 5.9 Клиентское приложение (браузер)

- Запросы к API с учётными данными идут в соответствии с политикой **CORS** среды (в продакшене — **явный список** разрешённых сайтов, без «разрешить всем»).
- Рекомендуется чек-лист для браузера (куки, сторонние расширения, смешанный HTTP/HTTPS) — отдельный документ для поддержки и внедрения.

---

## 6. Зоны ответственности (кто что настраивает)

| Зона | Ответственность |
|------|------------------|
| **Секреты и ключи** | `JWT_SECRET` и прочие секреты — только из защищённого хранилища среды; **никогда** в репозитории. |
| **Прокси и TLS** | Корректный HTTPS, доверенный список прокси, проброс заголовков — **эксплуатация** и **сетевая** команда. |
| **Redis и лимиты** | Включение Redis, лимиты по IP/email, режим при сбое Redis — **согласование ИБ и эксплуатации**. |
| **CORS** | Список разрешённых origin для prod — **владелец продукта / ИБ**, не разработчик «на глаз». |

---

## 7. Критерии приёмки с позиции ИБ (чек для релиза)

1. В продуктивной среде cookie долгой сессии отдаётся **только по HTTPS** (`Secure`).
2. Лимиты на вход **срабатывают** при искусственном превышении порога (smoke-тест или нагрузочный сценарий в тесте).
3. При включённом Redis **в ключах нет открытого email** (проверка по документации и выборочно по Redis).
4. Без доверенного прокси **поддельный** `X-Forwarded-For` **не меняет** IP для лимита (тест в среде, максимально близкой к бою).
5. После выхода повторный запрос с **старым** access-токеном (если он был отозван) **отклоняется** в рамках реализованной модели.
6. Логи содержат события ограничения входа в **машиночитаемом** виде для будущего подключения к SIEM.

---

## 8. Вне скоупа и ограничения честности

- Защита **от фишинга** пользователя (поддельная форма входа на чужом домене) — это **обучение пользователей** и **политика доменов**, не только код WMS.
- **Полная** защита от компрометации **устройства** пользователя (трояны, кейлоггеры) не решается только сервером.
- Глубокий **аудит** соответствия GDPR/152-ФЗ по персональным данным в email — отдельное юридическое ТЗ; здесь зафиксирован только технический шаг **не класть email в открытом виде** в ключи Redis для лимитов.
