# Логика отгрузок с планированием

------

## 1. Цель

Обеспечить учёт **отгрузок со склада** с возможностью:

- планирования будущих отгрузок
- фиксации фактической отгрузки
- контроля влияния на складские остатки

------

## 2. Сущность: Отгрузка

В системе фиксируется единая сущность — **Отгрузка**.

Каждая запись содержит:

- товар и его вариант
- количество
- дату отгрузки
- комментарий
- статус

------

## 3. Статусы

**Фиксированный набор:**

- **Ожидает отгрузки**
- **Отгружен**

------

### Правила:

- При создании записи:
  → статус = **Ожидает отгрузки**
- При подтверждении:
  → статус = **Отгружен**

------

## 4. Ключевое правило остатков

❗ В складские остатки попадают **только отгрузки со статусом “Отгружен”**

- “Ожидает отгрузки” не влияет на остатки
- при смене статуса выполняется уменьшение остатков

------

## 5. Логика даты отгрузки

### 5.1 Статус «Ожидает отгрузки»

- дата отгрузки может быть **любой**
  - в прошлом
  - сегодня
  - в будущем

👉 используется для планирования

------

### 5.2 Статус «Отгружен»

- дата отгрузки должна быть:
  → **≤ текущей даты**

❗ Запрещено:

- указывать будущую дату при фактической отгрузке

------

## 6. Логика товара и поиска варианта

Полностью соответствует основной логике системы:

### Обязательные поля:

- Дата отгрузки
- Штрих-код
- Цвет
- Размер (если требуется типом товара)

------

### Правила поиска:

- Одежда → штрих-код + цвет + размер
- Техника → штрих-код + цвет

------

### Результат:

**Если вариант найден:**

- отображается информационный блок товара

**Если не найден:**

- сообщение «Товар не найден»
- сохранение невозможно

------

## 7. Создание отгрузки

### 7.1 Поля формы

1. Дата отгрузки
2. Штрих-код
3. Цвет
4. Размер (если требуется)
5. Количество (≥ 1)
6. Комментарий (необязательно)

- блок найденного товара

------

### 7.2 Действия

- **Запланировать отгрузку**
  - статус = **Ожидает отгрузки**
  - дата может быть любой
  - не влияет на остатки
- **Подтвердить отгрузку**
  - статус = **Отгружен**
  - дата должна быть ≤ сегодня
  - уменьшает складские остатки
- **Отмена**
  - выход без сохранения

------

### Требования к кнопке планирования:

«Запланировать отгрузку»

Пользователь должен понимать:

- это может быть будущая отгрузка
- она не влияет на остатки

------

## 8. Редактирование

### Важно:

Редактирование доступно **на всех статусах**

------

### Поведение:

- можно изменять все поля
- при изменении товара выполняется повторный поиск варианта
- изменения сохраняются независимо от статуса

------

## 9. Финализация

### Действие:

- **Подтвердить отгрузку**

### Условия:

- найден вариант товара
- заполнены обязательные поля
- количество ≥ 1
- дата отгрузки ≤ текущей даты

------

### Результат:

- статус: Ожидает отгрузки → Отгружен
- уменьшаются складские остатки

------

## 10. Список отгрузок

### 10.1 Таблица

| Колонка    | Смысл              |
| ---------- | ------------------ |
| Дата       | дата отгрузки      |
| Статус     | Ожидает / Отгружен |
| Клиент     | получатель         |
| Штрих-код    | базовый штрих-код    |
| Название   | название товара    |
| Фото       | превью             |
| Цвет       |                    |
| Размер     |                    |
| Количество |                    |

------

### 10.2 Визуализация статусов

- **Отгружен** → зелёная заливка
- **Ожидает отгрузки** → жёлтая заливка

------

### 10.3 Фильтры

- Статус:
  - Ожидает отгрузки
  - Отгружен

Остальные фильтры без изменений.

------

## 11. Ограничения и правила

- нельзя создать запись без найденного варианта товара
- количество ≥ 1
- для “Отгружен” дата ≤ текущей
- “Ожидает отгрузки” допускает любую дату
- нельзя отгрузить больше доступного остатка
- редактирование доступно всегда

------

## 12. UX-логика

### Сценарий:

1. Пользователь создаёт отгрузку
2. Выбирает:
   - запланировать (в будущее или любое время)
   - или подтвердить (факт списания)
3. При необходимости редактирует в любой момент

------

## 13. Согласованность интерфейса

- полностью зеркально поступлениям
- единые статусы и паттерны
- одинаковая модель планирования + факта

------

## 14. Резюме

Модель:

→ Ожидает отгрузки → Отгружен

Даёт:

- планирование будущих отгрузок
- контроль фактического списания
- строгую защиту остатков

# Логика списка остатков

------

## 1. Цель

Обеспечить просмотр текущих **складских остатков товаров** с возможностью:

- контроля доступного количества
- анализа по товарам и вариантам
- сопоставления с поступлениями и отгрузками

------

## 2. Сущность: Остаток

Остаток — это **расчётное значение**, формируемое системой на основе:

- поступлений со статусом **«Принят»**
- отгрузок со статусом **«Отгружен»**

------

## 3. Формула расчёта

Остаток по товару/варианту:

→ **Остаток = Принято − Отгружено**

------

## 4. Принцип отображения

Каждая строка списка остатков соответствует:

- конкретному товару
- конкретному варианту (цвет + размер при необходимости)

------

## 5. Таблица остатков

⚠️ Ключевое требование:
структура таблицы **максимально совпадает с поступлениями и отгрузками**

------

### 5.1 Колонки таблицы

| Колонка  | Смысл                           |
| -------- | ------------------------------- |
| Штрих-код  | базовый штрих-код товара          |
| Название | название товара                 |
| Клиент   | клиент карточки товара          |
| Фото     | превью товара                   |
| Цвет     | вариант товара                  |
| Размер   | вариант товара (если применимо) |
| Остаток  | текущее доступное количество    |

------

### 5.2 Правила отображения

- если размер не используется → поле пустое или “—”
- если фото отсутствует → заглушка
- остаток всегда ≥ 0

------

## 6. Фильтры

Фильтры должны быть **аналогичны поступлениям и отгрузкам**:

1. Штрих-код
2. Клиент
3. Название товара
4. Цвет
5. Размер

------

## 7. Поведение данных

### 7.1 Обновление остатков

Остатки пересчитываются при:

- изменении статуса поступления → «Принят»
- изменении статуса отгрузки → «Отгружен»
- редактировании количества в этих сущностях

------

### 7.2 Ограничения

- отрицательные остатки запрещены
- система не позволяет отгрузить больше, чем доступно
- остатки не редактируются вручную

------

## 8. UX-логика

### Принцип:

Остатки — это **витрина состояния склада**, а не редактируемая сущность.

------

### Поведение интерфейса:

- только просмотр
- фильтрация и поиск
- отсутствие кнопок создания/редактирования

------

## 9. Согласованность интерфейса

Использовать патерны и глобальные компоненты

------

## 10. Резюме

Список остатков:

- отражает текущее состояние склада
- строится на основе поступлений и отгрузок
- имеет идентичную структуру таблицы с другими сущностями
- не допускает ручного изменения данных

# Логика остатков на дату (исторический срез склада)

------

## 1. Цель

Обеспечить возможность просмотра **состояния складских остатков на любую выбранную дату**, включая прошлые периоды.

Это позволяет:

- анализировать движение товаров во времени
- проверять корректность операций задним числом
- получать “снимок склада” на конкретный день

------

## 2. Сущность: Остатки на дату (Snapshot)

Остатки на дату — это **расчётное представление состояния склада на выбранный момент времени**.

Не хранится как отдельная сущность, а вычисляется на основе:

- поступлений со статусом **«Принят»**
- отгрузок со статусом **«Отгружен»**

------

## 3. Принцип расчёта

Для выбранной даты **D**:

→ учитываются только операции с датой ≤ D

------

### Формула:

Остаток на дату =
**Принятые поступления (≤ D) − Отгрузки (≤ D)**

------

## 4. Интерфейс: выбор даты

В списке остатков добавляется:

- поле **«Дата среза»**
- календарь (без времени)

------

### Поведение:

- по умолчанию = текущая дата
- при изменении даты → пересчёт таблицы

------

## 5. Таблица остатков на дату

⚠️ Структура полностью совпадает с обычными остатками

------

### 5.1 Колонки

| Колонка  | Смысл                        |
| -------- | ---------------------------- |
| Штрих-код  | базовый штрих-код товара       |
| Название | название товара              |
| Клиент   | клиент карточки товара       |
| Фото     | превью товара                |
| Цвет     | вариант товара               |
| Размер   | вариант товара               |
| Остаток  | количество на выбранную дату |

------

## 6. Фильтры

Сохраняются все фильтры из обычных остатков:

- Штрих-код
- Клиент
- Название
- Цвет
- Размер

- добавляется:

- Дата среза (обязательный фильтр контекста)

------

## 7. Правила расчёта

### 7.1 Входящие операции

Учитываются:

- поступления со статусом **«Принят»**
- только с датой ≤ выбранной даты

------

### 7.2 Исходящие операции

Учитываются:

- отгрузки со статусом **«Отгружен»**
- только с датой ≤ выбранной даты

------

### 7.3 Ограничения

- будущие операции не влияют на расчёт
- черновые / ожидающие статусы не учитываются

------

## 8. UX-логика

### Принцип:

Остатки на дату — это **режим анализа**, а не управления.

------

### Поведение интерфейса:

- нельзя редактировать данные
- только просмотр и фильтрация
- мгновенный пересчёт при смене даты

------

## 9. Визуальная согласованность

- таблица идентична текущим остаткам
- отличается только наличием выбора даты
- одинаковая структура колонок и фильтров

------

## 10. Важные сценарии использования

### Примеры:

- проверить остатки на конец месяца
- сверить склад перед инвентаризацией
- анализ движения товара по периодам

------

## 11. Ограничения

- расчёт только на стороне системы (не вручную)
- не хранить снапшоты в базе (если не требуется оптимизация)
- дата обязательна для любого запроса

------

## 12. Резюме

Остатки на дату:

- дают исторический срез склада
- используют ту же модель данных, что и текущие остатки
- позволяют анализировать движение товаров во времени
- полностью совместимы с существующей системой поступлений и отгрузок

# ТЗ: Проверка Excel-файла перед импортом

------

# 1. Цель

Реализовать единый этап полной проверки Excel-файла перед импортом данных в систему.

Проверка должна включать:

- проверку структуры файла
- проверку корректности данных
- проверку бизнес-логики
- проверку остатков
- поиск товаров и вариантов

Без записи данных в систему.

------

# 2. Общая логика

После загрузки файла пользователь нажимает кнопку:

**Проверить файл**

Система последовательно выполняет:

1. техническую проверку файла
2. проверку строк
3. проверку бизнес-логики
4. формирует итог проверки
5. показывает детализацию

- кнопка блокируется до завершения проверки
