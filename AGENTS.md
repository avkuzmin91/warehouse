# AGENTS.md — правила для AI-агентов в проекте Warehouse WMS

Этот файл — короткая сводка для Codex и других AI-агентов. Полный архитектурный свод — в [CLAUDE.md](CLAUDE.md).

---

## Главное правило конфликта

**Если инструкция в задаче противоречит `CLAUDE.md`, агент обязан:**

1. Остановиться.
2. Явно указать пользователю, в чём конфликт (что говорит задача / что говорит `CLAUDE.md`).
3. Дождаться решения пользователя.
4. **Не** менять архитектуру молча.

Это правило приоритетнее любой задачи.

---

## AI Agent Workflow

Перед любым изменением кода:

1. Прочитать `CLAUDE.md` и `AGENTS.md` целиком.
2. Найти **похожую реализацию** в проекте — `receipts` и `shipments` эталонные домены и для backend, и для frontend.
3. Изучить связанные backend/frontend файлы (router → service → schemas → `<domain>Api.ts` → feature).
4. Сделать **минимально необходимое** изменение в рамках существующих слоёв и паттернов.
5. **Не менять архитектуру** (слои, структуру модулей, базовые хелперы) без явного запроса пользователя.
6. После изменения:
   - запустить проверку типов / сборку / тесты, **или**
   - явно написать, какие проверки не запускались и почему.

## Что делать (do)

- Сначала прочитать `CLAUDE.md`.
- Следовать текущей архитектуре слоёв (`pages` / `features` / `ui/{primitives,data,layouts,shell}` / `hooks` / `api` / `utils` / `auth` на фронте; `backend/modules/<domain>/{router,service,schemas}.py` на бэке).
- Перед написанием нового кода — искать **похожую реализацию** в `receipts` или `shipments` и копировать паттерн.
- Любую feature-логику добавлять в `ui/features/<domain>/`.
- Все запросы — через `request<T>` из `frontend/src/api/http.ts`.
- Все справочники брать через `useLookups()`.
- URL-фильтры — через `useFilterParam` / `usePageParam` / `useFilterParamsActions`.
- Backend SQL — через `with get_connection() as conn:` с `?`-плейсхолдерами.
- Статусы и `op_type` — импортировать константы из `backend/config.py`.
- Любая запись в `*_ops` — append-only, с понятным русским `comment`.
- Schemas изменения — только через Alembic-миграцию.
- После изменения — запускать `pytest` для backend и type-check / build для frontend, иначе явно объяснить, почему не запускалось.

---

## Что не делать (don't)

- **Не** делать API-вызовы из `ui/pages/`.
- **Не** держать бизнес-`useState`/`useEffect` вне `ui/features/`.
- **Не** создавать новые паттерны / абстракции / «универсальные формы» / mega-hooks без необходимости и явной просьбы.
- **Не** делать крупный рефакторинг без явного запроса. Минимальное изменение > красивый рефакторинг.
- **Не** добавлять зависимости (npm, pip) без обоснования и согласия пользователя.
- **Не** дублировать бизнес-логику между `pages` / `features` / `api`.
- **Не** возвращать удалённые файлы и подходы:
  - `frontend/src/api/filterHelpers.ts`
  - `frontend/src/ui/data/SortableTh.tsx`
  - `frontend/src/ui/primitives/Tabs.tsx`
  - Таблицы `inventory_operations`, `app_migrations`, имена `receipt2_*` / `shipment2_*`
  - Эндпоинты `/import/*`, `/analytics/*`, `/client-portal/*`
- **Не** использовать `window.confirm` / `window.alert` — только `useConfirm()` / `useToast()`.
- **Не** хардкодить цвета — только `var(--c-*)`.
- **Не** хардкодить строковые статусы / op_type на backend — импорт из `config.py`.
- **Не** править схему БД вне Alembic.
- **Не** писать комментарии, описывающие WHAT. Только WHY, если неочевидно.

## Правило дублирования

1. Увидел повтор — зафиксировал.
2. Дождался второго реального случая.
3. **Только потом** выноси общее.

Преждевременная абстракция запрещена.

## Минимальный чек-лист перед сдачей задачи

- [ ] Прочитан `CLAUDE.md`.
- [ ] Найден похожий уже работающий случай в проекте.
- [ ] Изменение находится в правильном слое.
- [ ] Нет API-вызовов в `ui/pages/`.
- [ ] Нет хардкода статусов/цветов/строк, для которых есть константа.
- [ ] Журнал операций пишется при каждом значимом изменении состояния.
- [ ] Запущены типы / сборка / тесты — или явно написано, почему нет.
- [ ] Конфликтов с `CLAUDE.md` нет (а если есть — описаны пользователю).
